## Содержание статьи

В данной статье рассказано о назначение YAML Frontmatter (метаданных) в Markdown-файлах базы знаний, описаны основные

статье базы знаний. Приведен пример YAML Frontmatter для Markdown-файла базы знаний. 

## Назначение метаданных в Markdown-файлах

Метаданные (frontmatter) представляют собой структурированные текстовые блоки в начале статей базы знаний, которые 
выполняют роль карточек для классификации и фильтрации информации. Они критически важны для работы RAG-систем, позволяя 
ИИ точно и быстро находить актуальные документы по пяти ключевым группам параметров: идентификации, бизнес-контексту, 
жизненному циклу, безопасности и техническим настройкам.

Примеры влияния метаданных на качество выдачи ответов RAG-системой: 

- **Фильтрация**: Метаданные позволяют ограничивать поиск определенными категориями или датами.
- **Контекст**: Поля title и description могут добавляться к каждому фрагменту текста (чанку) при индексации, чтобы 
модель понимала, из какого документа пришел фрагмент, даже если заголовок был утерян при разбиении.
- **Актуальность**: Поле last_updated помогает приоритезировать свежие данные.

## Основные группы метаданных для RAG-систем

Рекомендуемая схема метаданных разделена на 5 ключевых групп:

- **Идентификация**: Обязательные технические данные для трассировки источников, исключения дубликатов и точного 
цитирования фрагментов (документов и чанков).
- **Бизнес-контекст**: Смысловые маркеры (тема, продукт, департамент, аудитория, язык), необходимые для точечного 
сужения зоны поиска по запросу пользователя (пре-фильтрация).
- **Управление жизненным циклом**: Параметры для контроля актуальности знаний, версионирования контента и отсева 
устаревших документов или черновиков.
- **Безопасность и доступ**: Корпоративные фильтры конфиденциальности и прав доступа (LDAP/AD группы), защищающие 
систему от утечки данных.
- **Технические данные**: Служебная информация (модель эмбеддингов, количество токенов, время загрузки), заполняемая 
RAG-системой автоматически на этапе индексации контента.

### Группа метаданных идентификации

Метаданные группы "идентификации" - обязательные технические данные для трассировки источников, исключения дубликатов и 
точного цитирования фрагментов (документов и чанков):

- Поле 'document_id':
    - Тип данных: String (UUID)
    - Описание и требования: Уникальный идентификатор исходного файла. Не должен меняться при обновлении версий, если 
    это тот же документ
- Поле 'chunk_id':
    - Тип данных: String 
    - Описание и требования: Уникальный ID конкретного фрагмента (чанка). Нужен для поиска ошибок и точного цитирования. 
    Присваивается автоматически на этапе загрузки документов в RAG-систему.
- Поле 'source_uri':
    - Тип данных: String   
    - Описание и требования: Путь к файлу в репозитории или URL. Позволяет пользователю перейти к оригиналу.
- Поле 'source_system':
    - Тип данных: String  
    - Описание и требования: Название системы-источника (например, «Confluence», «SharePoint», «Manual_v2»). Важно для 
    мультисорсовых баз.
- Поле 'file_name':
    - Тип данных: String  
    - Описание и требования: Оригинальное имя файла (например, setup_guide_v3.md). Полезно для отображения в интерфейсе.
- Поле 'page_number':
    - Тип данных: Integer   
    - Описание и требования: Если источник — PDF или книга. Для Markdown может быть опущено.

### Группа метаданных бизнес-контекста

Метаданные группы "бизнес-контекста" - самая важная группа для фильтрации информации RAG-системой. Метаданные группы 
представляют собой смысловые маркеры (тема, продукт, департамент, аудитория, язык), необходимые для точечного сужения 
зоны поиска по запросу пользователя (пре-фильтрация):

- Поле 'title':
    - Тип данных: String    
    - Описание и требования: Заголовок документа или раздела. Должен совпадать с H1 в файле.
- Поле 'topic':
    - Тип данных: String (Enum)   
    - Описание и требования: Основная тема. Требование: используйте контролируемый словарь терминов, чтобы избежать 
    разнобоя.
- Поле 'department':
    - Тип данных: String (Enum)    
    - Описание и требования: Департамент-владелец (Finance, IT, Sales). Используется для фильтрации по зоне 
    ответственности.
- Поле 'product':
    - Тип данных: String    
    - Описание и требования: Название продукта или модуля, к которому относится документ. Обязательно для продуктовых 
    баз знаний.
- Поле 'audience':
    - Тип данных: String (Enum)   
    - Описание и требования: Целевая аудитория: admin, end_user, developer, manager. Помогает отсечь сложные технические 
    детали от обычных пользователей.
- Поле 'language':
    - Тип данных: String (ISO)   
    - Описание и требования: Код языка (например, ru, en). Обязательно для мультиязычных баз, чтобы модель не смешивала 
    языки.
- Поле 'region':
    - Тип данных: String 
    - Описание и требования: Географическая привязка (EMEA, NA, Global). Важно для документов с региональными 
    особенностями (законы, налоги).
- Поле 'keywords':
    - Тип данных: Array[String]
    - Описание и требования: Список тегов. Требование: не более 5–10 тегов на документ. Использовать существительные, 
    а не фразы.
- Поле 'summary':
    - Тип данных: String 
    - Описание и требования: Краткое описание (1–2 предложения). Может генерироваться LLM автоматически или писаться 
    автором. Помогает при грубом поиске.

### Группа метаданных управления жизненным циклом

Метаданные группы "управления жизненным циклом" - параметры для контроля актуальности знаний, версионирования контента и 
отсева устаревших документов или черновиков, что напрямую влияет на достоверность ответов:

- Поле 'version':
    - тип данных: String 
    - описание и требования: Версия документа (например, 1.0, 2.1-beta). Помогает приоритезировать свежие данные.
- Поле 'status':
    - тип данных: String (Enum)
    - описание и требования: Статус зрелости: draft, review, published, archived. Требование: в поиск пускать только 
    published.
- Поле 'date_published':
    - тип данных:  Date (ISO 8601)
    - описание и требования: Дата публикации. Используется для сортировки "сначала новые".
- Поле 'last_updated':
    - тип данных: Date (ISO 8601)
    - описание и требования: Дата последнего изменения. Критично для динамических знаний (курсы валют, политики).
- Поле 'review_date':
    - тип данных: Date (ISO 8601)
    - описание и требования: Дата следующей плановой проверки. Позволяет автоматически помечать документ как "требующий 
    проверки".
- Поле 'owner':
    - тип данных: String
    - описание и требования: Владелец документа (человек или команда). Нужно для обратной связи и уточнения контента.

### Группа метаданных безопасности и доступа

Метаданные группы "безопасности и доступа" - корпоративные фильтры конфиденциальности и прав доступа (LDAP/AD группы), 
защищающие систему от утечки данных:

- Поле 'sensitivity_level':
    - тип данных: String (Enum)
    - описание и требования: Уровень чувствительности: public, internal, confidential, restricted. Требование: строгий 
    фильтр перед выдачей.
- Поле 'access_level':
    - тип данных: String (Enum)
    - описание и требования: Минимальная роль для доступа: guest, user, admin.
- Поле 'allowed_groups':
    - тип данных: Array[String]
    - описание и требования: Список групп (LDAP/AD), которым разрешен доступ. Например: ["HR_Managers", "IT_Security"].
- Поле 'tenant_id':
    - тип данных: String 
    - описание и требования: Уникальный идентификатор клиента (компании). Используется в облачной (SaaS) архитектуре для 
    жесткой изоляции данных: система по этому ID понимает, кому принадлежит информация, и полностью исключает риск 
    утечки данных между разными клиентами.

### Группа технических метаданных

Метаданные группы "технических данных" - служебная информация (модель эмбеддингов, количество токенов, время загрузки), 
заполняемая RAG-системой автоматически на этапе индексации контента:

- Поле 'ingestion_timestamp':
    - тип данных: Datetime 
    - описание и требования: Время загрузки в базу. Нужно для отладки и инкрементального обновления.
- Поле 'embedding_model':
    - тип данных: String 
    - описание и требования: Название модели, создавшей вектор (например, text-embedding-3-large). Нужно, если 
    планируется менять модели и делать ре-индексацию.
- Поле 'chunk_index':
    - тип данных: Integer 
    - описание и требования: Порядковый номер фрагмента (чанка) в документе (1 из 5). Полезно для восстановления 
    последовательности.
- Поле 'token_count':
    - тип данных: Integer 
    - описание и требования: Количество токенов во фрагменте (чанке). Нужно для контроля лимитов контекстного окна.

## Практические требования к реализации метаданных Markdown-файла

1. **Схема должна быть плоской**: Избегать вложенных JSON-объектов внутри метаданных. Использовать плоские ключи: 
product_name, product_version вместо product: {name, version}. 
2. **Типизация данных**: Строго соблюдать типы. Даты — только в формате ISO 8601 (2026-09-29T10:30:00Z), числа — без 
кавычек. Ошибки типов могут сломать фильтрацию.
3. **Контролируемые словари (Taxonomy)**: Для полей status, department, sensitivity_level использовать строго заданные 
значения (Enum). Не допускать вариативности ("Опубликовано" vs published), иначе фильтрация не сработает.
4. **Обязательные поля (Required)**: Определить минимальный набор, без которого документ не принимается в базу. Обычно 
это: document_id, title, status, sensitivity_level.

### Пример YAML Frontmatter для MD-файла

Пример блока с метаданными в начале статьи базы знаний (Markdown-файла):

```yaml
---
document_id: "a1b2c3d4-5678-90ef-ghij-klmnopqrstuv"
title: "Настройка двухфакторной аутентификации"
topic: "Security"
department: "IT"
product: "Corporate Portal"
audience: "end_user"
language: "ru"
status: "published"
version: "2.1"
sensitivity_level: "internal"
owner: "security_team@company.com"
last_updated: "2026-09-15"
keywords: ["2FA", "MFA", "login", "security"]
---
```

Примечание: выделение блока метаданных сверху и снизу тремя дефисами (---) - это зафиксированный стандарт для метаданных 
в экосистеме Markdown. Например, его "из коробки" понимают парсеры репозиториев GitHub, GitLab. GitHub и GitLab парсят 
этот блок как служебный. В режиме чтения (Preview) блок с метаданными выносится в служебную таблицу сверху, не мешая 
чтению основного текста.
