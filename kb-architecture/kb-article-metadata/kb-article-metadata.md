## Обзор статьи

В статье описано, что и как заполнять в блоке метаданных (YAML Frontmatter) статьи базы знаний при ручном создании
статьи. Для каждого поля указано, что записать, в каком формате и зачем поле нужно. Приведены правила синтаксиса,
порядок заполнения, пример блока и список для самопроверки.

[*Переход вверх*][3]

## Назначение метаданных

Метаданные (frontmatter) - структурированный блок в начале статьи, который служит карточкой статьи для [RAG-системы][20]
с гибридным поиском. По полям блока система фильтрует статьи до поиска, добавляет контекст к фрагментам текста (чанкам)
и отбирает актуальные данные.

[*Переход вверх*][3]

## Общие правила заполнения

### Расположение и синтаксис блока

Правила записи блока метаданных в файле:

- **Расположение**: Блок находится в самом начале файла. Блок открывается и закрывается строкой `---`, перед первой 
строкой нет пустых строк и других символов. Причина: Парсер находит блок только в начале файла.
- **Формат строки**: Ключ записывается строчными латинскими буквами в виде `ключ: значение` с одним пробелом после 
двоеточия. Причина: Единый формат читается одинаково всеми парсерами.
- **Длинные строковые значения**: Значение, которое не помещается в одну строку (обычно `summary`), записывать как
`summary: >-` и далее текст с отступом 4 пробела без кавычек, без пустых строк и без пробелов в конце строк. Причина:
Блок `>-` объединяет строки в одну через пробел и не добавляет перенос в конце значения. Кавычки внутри блока стали бы
частью значения.
- **Строки**: Все строковые значения записывать в двойных прямых кавычках, кроме значения в блоке `>-`. Двойные кавычки
внутри значения заменять на одинарные. Причина: Двойная кавычка внутри значения обрывает строку и ломает блок.
- **Отступы**: Использовать пробелы (4 пробела на каждый уровень), табуляцию не использовать. Причина: YAML не допускает
табуляцию в отступах.
- **Списки**: В YAML список записывается двумя способами: столбиком (каждый пункт с новой строки, начинается с `- `) или
в квадратных скобках через запятую. Короткие списки писать в одну строку в квадратных скобках: `["а", "б"]`. Если список
не помещается в 120 символов, переносить строку после запятой внутри скобок с отступом 4 пробела или писать столбиком.
Вопросы (`questions`) писать столбиком: каждый пункт начинается с 4 пробелов и `- `. Причина: Столбик удобнее для
длинных значений.
- **Пустые поля**: Если поле не нужно, строку с ключом удалить целиком. Пустые значения (`ключ: ""`, `ключ: []`) не 
оставлять. Причина: Пустое значение попадает в индекс и мешает фильтрации.

### Значения и справочники

Правила выбора значений полей:

- **Справочник значений**: Для полей `status`, `doc_type`, `department`, `topic`, `product`, `audience`, `region`, 
`sensitivity_level`, `language` и `tags` использовать только значения из `taxonomy.yml`. Значения записываются строчными 
латинскими буквами через подчёркивание. Причина: Вариант "Опубликовано" вместо `published` ломает фильтрацию.
- **Нужного значения нет**: Не выбирать неподходящее значение. Сообщить владельцу базы знаний, чтобы значение добавили в 
`taxonomy.yml`. Причина: Справочник - единый источник допустимых значений.
- **Слова в свободных полях**: В полях `keywords`, `aliases`, `summary` и `questions` писать обычные слова и устойчивые
словосочетания с пробелами: "база знаний", а не "база_знаний". Подчёркивание допустимо только в значениях из справочника
(`tags`, `topic` и других) и в названиях полей и файлов (`document_id`). Причина: Слово с подчёркиванием не совпадает со
словами запроса: поиск по словам воспринимает его как одно редкое слово, а модель эмбеддингов делит его на нетипичные
части. Это ухудшает и лексический, и семантический поиск.
- **Даты**: Записывать в формате `"ГГГГ-ММ-ДД"` в двойных кавычках, например, `"2026-10-11"`. Причина: Без кавычек 
парсер превращает значение в тип "дата", и часть инструментов отклоняет такой блок.

## Порядок заполнения блока метаданных

Блок заполняется по шагам создания статьи:

1. Скопировать блок из раздела "Пример блока метаданных" в начало нового файла и удалить поля, которые не нужны.
2. Создать новый `document_id` и записать заголовок `title`, равный H1 статьи.
3. На шаге сбора информации определить `sensitivity_level` и `allowed_groups`: от них зависит, какие материалы можно 
передавать ИИ.
4. Заполнить `doc_type`, `language`, `department`, `owner` и поля бизнес-контекста, установить `status: "draft"`. 
5. После аудита заполнить `summary`, `tags`, `keywords`, `aliases`, `questions`, записать `last_updated`, установить 
`status: "review"`.
6. При публикации установить `status: "published"`, записать `date_published`, `review_date` и `doc_version`.
7. Проверить блок по списку самопроверки.

## Поля идентификации

Поля группы идентификации однозначно определяют статью, её тип и язык:

- **`document_id`** (обязательное): Уникальный идентификатор статьи в формате UUID версии 4 в нижнем регистре, например, 
`"3f2a9c1e-7b4d-4e8a-9a12-5d6c0b8e1f47"`. Создаётся один раз командой `python3 -c "import uuid; print(uuid.uuid4())"`, 
не меняется при обновлениях и не копируется из другой статьи. Причина: На идентификатор ссылаются другие статьи.
- **`title`** (обязательное): Заголовок статьи, который посимвольно совпадает с H1. Причина: Заголовок добавляется к 
каждому фрагменту, и по нему определяется тема фрагмента.
- **`doc_type`** (обязательное): Тип содержимого, одно значение:
    - **`how_to`**: Инструкция, как выполнить задачу.
    - **`concept`**: Объяснение понятий и принципов.
    - **`reference`**: Справочная информация, правила, перечни.
    - **`troubleshooting`**: Диагностика и устранение проблем.
    - **`policy`**: Регламент или политика.
    - **`faq`**: Вопросы и ответы.
- **`language`** (обязательное): Код языка статьи по ISO 639-1: `ru` - русский, `en` - английский. Один файл - один
язык. Перевод оформляется отдельным файлом с собственным `document_id` и связывается через `related`. Причина: Модель не
должна смешивать языки в одном ответе.

## Поля бизнес-контекста

Поля бизнес-контекста сужают зону поиска до начала поиска по тексту:

- **`topic`** (рекомендуется): Основная тема статьи, одно значение из справочника. Причина: Тема сужает поиск до начала
поиска по тексту. Значения:
    - **`security`**: Информационная безопасность.
    - **`onboarding`**: Адаптация и обучение новых сотрудников.
    - **`billing`**: Выставление счетов и оплата.
    - **`integrations`**: Интеграции между системами.
    - **`infrastructure`**: Серверы, сети, рабочие места и другая ИТ-инфраструктура.
    - **`compliance`**: Соблюдение законодательных и внутренних требований.
    - **`hr_processes`**: Кадровые процессы (приём, отпуска, увольнение).
    - **`product_usage`**: Использование продукта пользователем.
    - **`knowledge_management`**: Создание и ведение базы знаний.
    - **`standards`**: Стандарты и нормативные документы.
- **`department`** (обязательное): Подразделение, которое отвечает за содержание статьи (не подразделение читателей),
одно значение. Причина: Поле позволяет фильтровать статьи по зоне ответственности. Значения:
    - **`it`**: Информационные технологии и ИТ-инфраструктура.
    - **`finance`**: Финансы, бухгалтерия, бюджетирование.
    - **`sales`**: Продажи и работа с клиентами.
    - **`hr`**: Управление персоналом.
    - **`legal`**: Юридические вопросы и договоры.
    - **`support`**: Техническая поддержка пользователей и клиентов.
    - **`marketing`**: Маркетинг и коммуникации.
    - **`operations`**: Операционная деятельность и производственные процессы.
- **`product`** (обязательное для продуктовой базы знаний): Продукт или модуль, к которому относится статья, одно
значение из справочника. Сейчас в справочнике одно значение: `corporate_portal` (корпоративный портал компании).
Причина: Поле отделяет инструкции разных продуктов.
- **`product_version`** (рекомендуется, если указан `product`): Версия продукта строкой, например, `"4.x"` или `"4.2"`. 
Не путать с `doc_version`. Причина: Без версии модель смешивает инструкции разных релизов.
- **`audience`** (рекомендуется): Основной читатель статьи, одно значение. Причина: Поле отсекает технические детали для
обычных пользователей. Значения:
    - **`end_user`**: Конечный пользователь продукта или сервиса.
    - **`admin`**: Администратор системы.
    - **`developer`**: Разработчик.
    - **`manager`**: Руководитель.
- **`region`** (по условию): Регион статьи, одно значение. Указывать только для статей с региональными особенностями
(законы, налоги, стандарты). Причина: Лишнее значение сужает выдачу. Значения:
    - **`global`**: Статья действует во всех регионах. Нужна, чтобы отличить общую статью от региональных версий той же
      темы.
    - **`emea`**: Европа, Ближний Восток и Африка.
    - **`na`**: Северная Америка.
    - **`apac`**: Азиатско-Тихоокеанский регион.
    - **`latam`**: Латинская Америка.
    - **`cis`**: Страны СНГ.

## Поля поискового обогащения

Поля поискового обогащения повышают полноту и точность гибридного поиска:

- **`summary`** (обязательное): Краткое описание статьи в 1-2 предложениях, 20-300 символов. Содержит название предмета 
статьи и то, что читатель в ней найдёт. Не начинать со слов "Эта статья". Обновлять при изменении содержания. Причина: 
Описание добавляется к каждому фрагменту статьи, поэтому должно быть понятно без остального текста.
- **`tags`** (рекомендуется): От 1 до 5 тегов из справочника `taxonomy.yml` (в отличие от ключевых слов, которые пишутся
свободно). Причина: Теги из справочника ищутся точно, а свободные формулировки - нет. Теги по группам:
    - **Доступ и безопасность**: `authentication` (аутентификация), `mfa` (многофакторная аутентификация), `sso` (единый
      вход), `access_control` (управление доступом), `passwords` (пароли), `vpn` (удалённый доступ).
    - **Системы и данные**: `email` (электронная почта), `reporting` (отчётность), `api` (программные интерфейсы), `git`
      (система контроля версий).
    - **База знаний и ИИ**: `knowledge_base` (база знаний), `rag` (RAG-системы), `markdown` (формат Markdown),
      `formatting` (оформление текста), `ai_content` (материалы, созданные ИИ), `verification` (проверка и верификация).
    - **Стандарты и качество**: `iso` (стандарты ISO), `square` (серия SQuaRE), `software_quality` (качество
      программного обеспечения), `software_lifecycle` (жизненный цикл программного обеспечения), `requirements`
      (требования), `bibliography` (библиография и источники).
- **`keywords`** (рекомендуется): До 10 ключевых слов для поиска по словам. Использовать существительные, устойчивые 
термины и словосочетания из текста, а не целые предложения. Причина: Лексический поиск сопоставляет слова запроса со 
словами из этого поля.
- **`aliases`** (рекомендуется): До 10 вариантов названия предмета статьи, которых нет в `title` и `keywords`: синонимы, 
аббревиатуры, прежние названия, разговорные формулировки, английские термины. Причина: Пользователь ищет по тому слову, 
которое знает, а не по слову из статьи.
- **`questions`** (рекомендуется): От 2 до 5 вопросов, на которые отвечает статья, в формулировке пользователя. Каждый 
вопрос полный, с названием предмета, до 200 символов, заканчивается знаком "?". Причина: Формулировка запроса совпадает 
с формулировкой вопроса лучше, чем с текстом статьи.
- **`related`** (рекомендуется): Список `document_id` связанных статей. Идентификаторы копировать из блока метаданных 
этих статей. Связь односторонняя: обратную связь добавить в другой статье. Причина: Связанные статьи расширяют контекст 
ответа.

## Поля жизненного цикла

Поля жизненного цикла управляют актуальностью статьи:

- **`status`** (обязательное): Статус статьи. В поиск попадают только статьи со статусом `published`:
    - **`draft`**: Черновик, шаги 1-3 создания статьи.
    - **`review`**: Статья на проверке, шаги 4-5.
    - **`published`**: Статья опубликована, шаг 6.
    - **`archived`**: Статья устарела и заменена другой, указывается `replaced_by`.
- **`doc_version`** (рекомендуется): Версия статьи строкой в формате `"1.0"`, `"2.1"`, `"2.1-beta"`. Первая публикация - 
`"1.0"`. Первое число увеличивать при изменении смысла или порядка действий, второе - при дополнениях. Причина: Версия 
показывает, насколько изменилась статья.
- **`date_published`** (рекомендуется): Дата первой публикации. Записать при первом переводе в `published`, при 
обновлениях не менять. Для черновика поле не указывать.
- **`last_updated`** (обязательное): Дата последнего содержательного изменения. Менять при изменении фактов и шагов, не
  менять при исправлении опечаток. Причина: Дата показывает актуальность данных.
- **`review_date`** (рекомендуется): Дата следующей плановой проверки, не раньше `last_updated`. Для быстро меняющихся 
данных - через 3 месяца, для обычных статей - через 6, для стабильных - через 12. Причина: Дата сообщает владельцу, что 
статью пора проверить.
- **`valid_until`** (по условию): Дата окончания действия статьи (акции, временные регламенты). После этой даты статья 
исключается из выдачи. Причина: Срок действия защищает от устаревших ответов.
- **`owner`** (обязательное): Владелец статьи - автор (ИФ) или команда, одно значение. Причина: Владелец отвечает за 
актуальность статьи.
- **`supersedes`** (по условию): `document_id` статьи, которую заменяет эта статья.
- **`replaced_by`** (обязательное для `archived`): `document_id` статьи, которая заменила архивную. Причина: 
Пользователь, нашедший архивную статью, получает ссылку на актуальную.

## Поля безопасности и доступа

Поля безопасности определяют, кто видит статью в результатах поиска:

- **`sensitivity_level`** (обязательное): Уровень чувствительности, одно значение. Определять по самым чувствительным 
сведениям статьи, при сомнении выбирать более высокий уровень:
    - **`public`**: Информацию можно публиковать без ограничений.
    - **`internal`**: Информация только для сотрудников компании.
    - **`confidential`**: Информация для ограниченного круга сотрудников.
    - **`restricted`**: Информация для строго определённого круга лиц.
- **`allowed_groups`** (обязательное): Список групп каталога пользователей (LDAP/AD), которым разрешён доступ, минимум 
одна группа. Названия групп копировать из каталога без изменений, например, `["HR_Managers", "IT_Security"]`. Причина: 
Это единственное поле, по которому проверяются права доступа, а статья без групп не индексируется.
- **Общие группы**: Для уровней `confidential` и `restricted` не использовать общие группы `all_employees`, `everyone`, 
`users`. Причина: Общая группа открывает закрытую статью всем сотрудникам.

## Самопроверка блока метаданных

Перед публикацией проверить блок:

- **Расположение**: Блок первый в файле, открыт и закрыт строками `---`, табуляций и пустых полей нет.
- **Обязательные поля**: Заполнены `document_id`, `title`, `summary`, `doc_type`, `status`, `language`, `department`, 
`owner`, `sensitivity_level`, `allowed_groups`, `last_updated`.
- **Идентификация**: `title` посимвольно совпадает с H1, `document_id` создан заново.
- **Значения**: Значения полей со справочником есть в `taxonomy.yml`, даты записаны как `"ГГГГ-ММ-ДД"`, `review_date` не 
раньше `last_updated`.
- **Статус и доступ**: Для `archived` указан `replaced_by`. Для `confidential` и `restricted` нет общих групп.
- **Лишнее**: В блоке нет пустых полей и полей, которые не описаны в статье.

После ручной проверки блок можно проверить скриптом `validate_frontmatter.py`.
