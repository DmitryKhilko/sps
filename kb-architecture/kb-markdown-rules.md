## Содержание статьи

В статье собраны правила и практические советы по оформлению файлов, текстов и метаданных в базе знаний. Это необходимо 
для поддержания семантической целостности (смысловой точности и логики данных) всей информации базы знаний и правильной 
подготовки информации базы знаний к работе с [RAG-системами][6]. 

Текст для [RAG][8] должен писаться иначе, чем текст для чтения человеком. Главная цель - сделать каждый абзац статьи 
базы знаний семантически плотным (в минимальный объем слов упакован максимум полезного смысла и фактов) и независимым. 
Также качество парсинга статей базы знаний RAG-системой напрямую зависит от чистоты синтаксиса Markdown.

В результате подготовки информации базы знаний по приведенным правилам RAG-система сможет легко находить нужный 
контекст, точнее извлекать важные фрагменты и генерировать максимально качественные и релевантные ответы.

## Иерархия каталогов, имена каталогов и файлов базы знаний 

При создании каталогов и файлов базы знаний выполнить следующие требования:

- Использовать плоскую структуру с уникальными именами файлов или использовать каталоги без большой вложенности: не 
превышать 5–7 уровней вложенности. В RAG-системе путь к файлу часто используется как метаданные категории. Слишком 
длинные пути усложняют фильтрацию.
- Организация файлов должна отражать логическую структуру базы знаний, что упрощает навигацию как для людей, так и для 
алгоритмов извлечения RAG-системы. 
- Имя файла должно дублировать тему статьи и быть понятным человеку. Если статья называется "Технологический стек базы 
знаний", файл назвать kb-tech-stack.md, а не doc-v2-final.md. RAG-система использует имя файла как "якорь" для 
поиска. Чёткое имя повышает релевантность выдачи.
- Имена файлов и каталогов содержат только латиницу без пробелов, например, architecture-requirements.md. Такие имена 
файлов и каталогов гарантирует совместимость на любых серверах (Linux/Windows) и корректность URL.
- В именах файлов и каталогов для разделения слов использовать символ дефиса (-). В RAG-системе дефис гарантирует, 
что ИИ правильно "прочитает" название файла по отдельным словам и сможет быстро найти его как по ключевым словам, так и 
по смыслу. 
- В именах файлов и каталогов использовать только нижний регистр для предотвращении путаницы. Например, в Linux 
Install.md и install.md - разные файлы.
- Длина имени файлов и каталогов до 25 символов - рекомендация архивных стандартов для надежности.

## Контекст и независимость статей, разделов статей

При создании текста статьи базы знаний выполнить следующие требования:

- **Единая тема на файл**: Каждый файл .md должен охватывать одну конкретную тему или сущность. Это предотвращает 
смешивание несвязанных контекстов внутри одного документа, что ухудшает качество поиска. Вместо одного большого файла на 
500 страниц создать несколько файлов, описывающих отдельные темы. Это позволит чанкеру выделять смысловые блоки без 
потери контекста.
- **Минимально возможное количество местоимений**: В пределах одного текстового раздела статьи (под одним заголовком) 
минимизировать использование слов "он", "она", "этот", "их", "данный". Если абзац будет вырезан из контекста при 
чанкинге, модель не поймет, к чему относится местоимение. Рекомендуется заменять местоимения конкретикой: вместо "этот 
процесс" писать "согласование требований", вместо "независимость статей и их разделов" писать "независимость статей и 
разделов статей".
- **Отсутствие канцеляризмов и эмоций**: Писать текст максимально просто, сухо и только по делу. Избегать канцеляризмов, 
например, вместо "осуществлять деятельность" написать "работать", вместо "в целях обеспечения" написать "чтобы". 
Эмоциональные слова вроде "эффективный", "быстрый" или "важнейший" засоряют текст и путают алгоритмы поиска. Отсутствие 
канцеляризмов и эмоций уменьшает расход токенов языковой модели, защищает языковую модель от галлюцинаций, помогаете ИИ 
извлекать чистую суть для генерации точного ответа.
-**Правило "первого предложения"**: Начинать каждый раздел (после заголовка) статьи с краткого резюме или определения. 
Первое предложение должно отвечать на вопрос "О чем этот раздел?". Это помогает модели быстро классифицировать чанк.
- **Самодостаточность (тематическая изоляция) разделов статьи**: Каждый раздел (после заголовка) статьи должен иметь 
смысл даже без чтения предыдущих блоков. Избегать фраз в стиле "Как написано в разделе выше..." - при поиске ИИ может 
вырвать этот чанк отдельно, и контекст потеряется. Внутри текстового раздела статьи повторять ключевые термины и 
контекст, необходимые для понимания. 
- **Тезисные формулировки**: Использовать списки везде, где можно обойтись без связующего художественного текста.

## Рекомендуемые размеры статьи для использования в RAG-системе

Для точного поиска по базе знаний, помещенной в RAG-систему, авторам необходимо придерживаться рекомендованного 
количества символов с пробелами для статьи (одного файла), входящих в статью разделов (текст под заголовком), входящих в 
раздел абзацев, списков. 



- **Элемент**: Статья
    - Рекомендуемый размер, символов с пробелами: 6000-12000
    - Допустимый размер, символов с пробелами: 3000-6000 / 12000-15000
    - Желательно переработать, символов с пробелами: <3000 / >15000
    - Что делать при <3000 символов с пробелами: Объединить в одну статью.
    - Что делать при >15000 символов с пробелами: Разделить на несколько статей.
- **Элемент**: Раздел H2
    - Рекомендуемый размер, символов с пробелами: 1500-3500
    - Допустимый размер, символов с пробелами: 800-1500 / 3500-4000
    - Желательно переработать, символов с пробелами: <800 / >4000
    - Что делать при <800 символов с пробелами: Объединить в один раздел H2.
    - Что делать при >4000 символов с пробелами: Разбить на несколько разделов H2 или добавить подразделы H3.
- **Элемент**: Подраздел H3
    - Рекомендуемый размер, символов с пробелами: 700-1800
    - Допустимый размер, символов с пробелами:  500-700 / 1800-2000
    - Желательно переработать, символов с пробелами: <500 / >2000
    - Что делать при <500 символов с пробелами: Объединить в один подраздел H3.
    - Что делать при >2000 символов с пробелами: Разбить на несколько подразделов H3.
- **Элемент**: Абзац
    - Рекомендуемый размер, символов с пробелами: 400-900
    - Допустимый размер, символов с пробелами:   200–400 / 900–1200
    - Желательно переработать, символов с пробелами: <200 / >1200
    - Что делать при <500 символов с пробелами: Объединить в один абзац, преобразовать в список.
    - Что делать при >2000 символов с пробелами: Разбить на несколько абзацев, преобразовать в список.
- **Элемент**: Пункт списка
    - Рекомендуемый размер, символов с пробелами: 100-500
    - Допустимый размер, символов с пробелами:   500-700
    - Желательно переработать, символов с пробелами: >700
    - Что делать при >700 символов с пробелами: Разбить на несколько пунктов.
- **Элемент**: Таблица
    - Рекомендуемый размер, строк: до 10-15
    - Максимальный размер, строк: 20 
    - Что делать при превышении рекомендуемого размера: Разделить строки таблицы по смыслу.


**Указанные размеры являются рекомендациями по подготовке материалов базы знаний и не зависят от конкретной используемой LLM. После выбора модели и настройки RAG параметры чанкинга могут быть оптимизированы на уровне технической реализации без изменения исходных статей.**

Это позволит сейчас спокойно создавать базу, а потом менять **chunk size / overlap / retrieval**, не переписывая сами статьи.
То есть я бы разделил ответственность:
**Автор:**
> пишет хорошо структурированную статью заданного размера.
**RAG-система:**
> сама решает, как эту статью технически разбить на чанки для конкретной модели.



### Статья
**Ориентир: 6–12 тыс. символов.**
Статья должна отвечать на **один основной вопрос или описывать одну законченную тему**.
Например:
> «Создание пользователя»
а не:
> «Пользователи, роли, авторизация, блокировка, восстановление пароля и аудит».

---

### Раздел
**Ориентир: 1,5–3,5 тыс. символов.**
Один H2 — **одна подтема**.
Если раздел начинает приближаться к 4 000 символов — посмотреть, нельзя ли выделить H3.
В исходном документе уже используется порог 4 800 символов для проблемного H2/H3; я бы сохранил более консервативный рабочий предел 4 000.

---

### Абзац
**Ориентир: 400–900 символов.**
Главное правило:
> **Один абзац — одна законченная мысль.**
Если абзац получается на 1 500–2 000 символов, почти всегда стоит проверить, не содержит ли он несколько самостоятельных мыслей.
Это соответствует заложенному в исходном документе принципу, что слишком плотный блок следует разбивать на несколько абзацев или подпунктов.





### Рекомендуемый размер статьи

Рекомендуемый размер статьи (одного файла) находится в диапазоне:

- **Токены**: 500 – 2500 токенов.
- **Символы**: 3 000 – 15000 символов.
- **Слова**: 500 – 2000 слов.

Обоснование выбора рекомендованного размера статьи (одного файла):

- **Целостность контекста**: Файл такого размера обычно помещается в одно контекстное окно модели (или занимает его 
небольшую часть). Это позволяет RAG-системе загрузить весь файл как "родительский документ" для стратегии Parent-Child 
Retrieval, сохранив все связи.
- **Управляемость**: Статьи короче 500 токенов часто слишком поверхностны и требуют объединения. Статьи длиннее 3000 
токенов становятся "монолитами", где трудно найти конкретную деталь, и их приходится агрессивно чанковать, теряя 
контекст.

### Рекомендуемый размер раздела

Рекомендуемый размер раздела (под заголовком) находится в диапазоне:

- **Токены**: 150 – 600 токенов.
- **Символы**: 1000 – 4000 символов.
- **Абзацы**: 2 – 5 абзацев (или один сложный список).

Обоснование выбора рекомендованного размера раздела (под заголовком):

- **Попадание в чанк**: Большинство RAG-систем настроены на чанки размером 512 – 1024 токена. Раздел размером 300 – 500 
токенов идеально помещается в один чанк целиком, не разрываясь на части. Это сохраняет смысловую целостность.
- **Фокус**: Раздел должен раскрывать одну подтему. Если раздел становится больше 800 токенов, скорее всего, в нем 
смешано несколько тем, и его стоит разбить на подразделы (H3).

### Стратегия "Матрешки"

Для оптимальной структуры статьи базы знаний использовать иерархический подход:

1. **Файл (Статья)**: ~1500 токенов (~9000 символов). Отвечает на вопрос «Что такое X?» или «Как работать с модулем X?».
2. **Раздел (H2)**: ~400 токенов (~2400 символов). Отвечает на подвопрос «Как настроить X?», «Какие есть ограничения у X?».
3. **Подраздел (H3) или Абзац**: ~150 токенов (~600 символов). Конкретный факт, шаг инструкции или определение.

### Признаки того, что размер статьи/раздела неверен

Как быстро оценить размер статьи/раздела:

- 1 токен ≈ 4–6 символов (включая пробелы) для европейских языков.
- Средняя статья (1500 токенов) ≈ ~9000 символов.

Используйте приведенные ниже ориентиры при планировании структуры базы знаний. Если файл или раздел выходит за рамки, 
это сигнал к пересмотру структуры.

- **Файл (Статья)** > 3000 токенов (> 18000 символов)
    - **Проблема**: "Стена текста". Трудно найти конкретную деталь, высокий риск потери контекста при чанкинге.
    - **Решение**: Разбить на несколько отдельных статей по подтемам. Каждая новая статья должна быть самодостаточной.
- **Файл (Статья)** < 300 токенов (< 1800 символов)
    - **Проблема**: Слишком мелко. Потеря контекста, невозможно построить полноценный Parent-Child контекст.
    - **Решение**: Объединить с соседними темами в одну статью. Исключение — короткие FAQ или справки по одной команде.
- **Раздел (H2/H3)** > 800 токенов (> 4800 символов)
    - **Проблема**: Чанкер с высокой вероятностью разрежет раздел посередине, нарушив логику повествования.
    - **Решение**: Добавить подзаголовки (H3/H4), разбить текст на списки или вынести часть информации в отдельный 
    раздел.
- **Раздел (H2/H3)** < 100 токенов (< 600 символов)
    - **Проблема**: Бессмысленный микро-раздел. Заголовок занимает больше места, чем контент.
    - **Решение**: Объединить с соседним разделом или убрать заголовок, оформив мысль как абзац или пункт списка.
- **Абзац / Список** > 300 токенов (> 1800 символов)
    - **Проблема**: Слишком плотный блок информации. Трудно выделить ключевую мысль для эмбеддинга.
    - **Решение**: Разбить на несколько абзацев или подпунктов списка. Убедиться, что каждый абзац несет одну 
    законченную мысль.




Плотность информации — это количество полезных фактов, инструкций и уникальных данных на один абзац или страницу текста. Проще говоря, это показатель того, насколько сильно текст «спрессован» и очищен от лишних слов.
• Высокая плотность: Текст состоит только из конкретики. Каждое предложение несет новую мысль, цифру, команду или правило. Пример — техническая документация, API-справка или лаконичный чек-лист. Здесь на 1000 знаков может быть 10 ключевых фактов.
• Низкая плотность: В тексте много рассуждений, вводных слов, повторов и метафор («воды»). Пример — художественная литература, публицистика или рекламные статьи. На те же 1000 знаков там может приходиться всего 1–2 полезных факта.
Почему плотность информации важна для разделения файлов под RAG?
Алгоритмы RAG нарезают файлы на небольшие кусочки (чанки).
• Если у текста высокая плотность, разделы нужно делать короче, иначе в один чанк попадет слишком много разных инструкций, искусственный интеллект «запутается» в них или потеряет детали.
• Если у текста низкая плотность, разделы можно делать длиннее, чтобы ИИ не вырвал фразу из контекста и смог уловить общую мысль среди сопутствующих рассуждений.







## Заголовки статьи базы знаний

При создании заголовков статьи базы знаний выполнить следующие требования:

- **Принцип "один файл - один заголовок # H1"**: Главное название статьи должно быть строго в первой строчке. Не 
использовать больше одного заголовка # H1 в документе. Заголовок # H1 дублирует поле title в метаданных.
- **Иерархия заголовков**: Использовать строгую иерархию заголовков (## H2 -> ### H3 -> #### H4 и т.д.). 
Заголовки служат естественными границами для чанкинга (разбиения текста). RAG-системы часто используют заголовки как 
точки разрыва, чтобы сохранять смысловую целостность блоков.
- **Рекомендуемая глубина заголовков**: Укладываться в 3 уровня (# H1 -> ## H2 -> ### H4). Это обеспечит идеальную 
структуру для RAG, чистое оглавление и удобную навигацию.
    - H1: Обязательно 1 (заголовок файла).
    - H2: Основной (использовать активно).
    - H3: Рекомендуемый (для детализации). 
    - H4: Избегать (заменять списками со вложенностью или жирным текстом).
- **Заголовки должны быть описательного характера и содержать ключевые слова**: Плохо: "Общие сведения", "Настройки". 
Хорошо: "Итеративно-инкрементный подход к созданию базы знаний", "Устранение ошибок подключения к базе данных".

- Сквозная навигация. RAG-система строит карту взаимосвязей между документами. Для этого ему нужны чёткие указатели. 
    - Использовать явные ссылки. Никогда не упоминать другие документы просто текстом. Всегда делать их кликабельными 
    ссылками Markdown: [Название](путь).
    - Использовать только относительные пути. Не использовать домены (https://...) или абсолютные пути диска (C:/...). 
    Ссылки должны вести на файлы внутри репозитория базы знаний ([Текст](../соседняя_папка/file.md)).  
    - Если в статье множество раз употребляется термин, описанный в глоссарии, ссылаться на термин в глоссарии только 
    при первом упоминании в тексте статьи (но не в заголовках статьи). Для RAG гиперссылки играют роль структурных 
    маркеров, но их избыток может навредить.
        - Семантический шум: При чанкинге (разбиении текста) гиперссылки часто превращаются в Markdown-конструкцию 
        [термин](url). Если таких конструкций в чанке десятки, они могут «размывать» векторное представление текста, 
        добавляя шум в эмбеддинги.
        - Разрыв контекста: Чрезмерное использование ссылок может привести к тому, что при парсинге текст будет разбит 
        на множество мелких фрагментов, что усложнит модели восстановление связного контекста.
        - Польза ссылок (Link-Aware RAG): Сами по себе ссылки полезны - продвинутые RAG-системы используют их для 
        навигации (агенты могут «переходить» по ссылкам в глоссарий для уточнения сущностей). Но для этого достаточно 
        одной качественной ссылки на термин, а не сотни одинаковых.

### Форматирование текста статьи 

При форматировании создаваемого текста статьи базы знаний выполнить следующие условия:
- **Ограничения длины строки при наборе текста в VS Code**: При наборе текста статьи базы знаний использовать 
ограничение длины строки в 80/120 символов. Ограничение делает текст более удобным для восприятия, но при этом не 
ухудшает качество ответов RAG-системы. При этом необходимо следить, чтобы из-за переносов не было разрывов в ссылках, 
словах, блоках кода. Для настройки ограничения в settings.json добавить ключ-значение ""editor.rulers": [120]". 
- **Отделение заголовков пустыми строками сверху и снизу**: Согласно спецификации CommonMark (стандарт Markdown), 
заголовок должен быть окружен пустыми строками, чтобы корректно распознаваться и обрабатываться RAG-системой. 
- **Между абзацами текста оставлять одну пустую строку**: Пустая строка - это чёткий сигнал для RAG-системы о конце 
одной мысли и начале другой мысли. Без пустой строки два соседних абзаца сольются в один сплошной блок текста при 
обработке их RAG-системой. 
- **Список предпочтительнее нескольких абзацев**: Для базы знаний, оптимизированной под RAG, почти всегда лучше 
использовать список, даже если факты многострочные. 
    - **Символы списка (-, 1.) работают как четкие разделители**: 
        - Алгоритм разбиения текста на смысловые части (чанки) видит начало нового пункта и может использовать это как 
        безопасную точку для разрыва текста. Это гарантирует, что один факт не «прилипнет» к другому и не будет разорван 
        посередине. 
        - Модели LLM обучены на огромном количестве структурированных данных. Список для неё - это сигнал: "Здесь 
        перечислены однородные сущности". Это упрощает извлечение конкретного факта по запросу.
    - **Символы списка (-, 1.) изолируют факты**: В списке каждый пункт воспринимается как отдельная логическая единица. 
    Например, при запросе "Какие есть ограничения по памяти?" в списке модель легко найдёт пункт "Ограничения 
    памяти: ..." и скопирует его. Если факты написаны сплошным текстом, модель может "потерять" границу между фактами и 
    выдать лишнюю информацию или, наоборот, обрезать ответ.   

Список создает явную структуру, которую легче парсить, чанковать и 
извлекать. Отдельные абзацы без маркеров («стена текста») хуже поддаются обработке. 



- **Не добавлять пустую строку между пунктами списка**: Пункты списка должны идти сплошным блоком. Пустые строки между 
ними создают разрывы, которые могут восприниматься RAG-системой как отдельные списки. 
- **Пункт списка не должен быть более 3-4 строк**: Если пункт становится большим (более 3 - 4 строк), разбить пункт на 
подпункты или вынести в отдельный абзац. Это упростит разбивку и извлечение информации RAG-системой.  
- **Явные разделители**: Использовать горизонтальные линии (---) только для разделения крупных смысловых блоков, но 
основным средством деления должны оставаться заголовки.
- **Не использовать таблиц в тексте**: Таблицы сложны для парсинга и часто "ломаются" при чанкинге - строки таблицы 
могут попасть в разные векторы. Рекомендовано заменить таблицы на маркированные или нумерованные списки с чёткой 
структурой.
- **Код и технические блоки**: 
    - Блоки кода (```) должны быть изолированы: Код отделяется от остального текста пустыми строками (сверху и снизу) и 
    не смешивается с обычными абзацами внутри одного блока. 
    - Не смешивать код и пояснения внутри блока кода: Внутри тройных кавычек (```) должен быть только код. Никаких 
    комментариев на человеческом языке, если они не являются частью синтаксиса языка программирования.
    - Явно указывать язык программирования сразу после открывающих кавычек. Без указания языка код будет разбит просто 
    по строкам, что может разрезать функцию посередине.
    - Логически связанные куски кода должны быть расположены вместе в блоке кода.
    - Для технического контента рекомендуется меньший размер чанков (100–200 токенов), чтобы код не обрезался посередине 
    функции.
    Пример:
    
    ```
    python
    import os
    import sys
    ```

- **Использовать вводные предложения для списков**: Перед списком всегда приводить полноценное предложение, объясняющее суть 
перечисления. Вводное (поясняющее) предложение для списков связывают элементы списка в единый смысловой блок. Между 
вводным предложением и списком нужно оставлять пустую строку, чтобы парсер RAG-системы корректно распознал начало списка. 


Всегда ставьте пустую строку перед списком, если он идет после обычного текста или заголовка. Это гарантирует корректный рендеринг и правильную работу парсеров RAG-системы.



- **Начинать каждый пункт списка с новой строки**: Пункты списка не располагать в одну строчку через запятую (точку с 
запятой).
- **Использовать единый символ выделения пункта маркированного списка**: Для единообразного представления пунктов 
маркированных списков по все базе знаний использовать один и тот же символ: звездочку * или дефис -.
- **Использовать нумерованные списки только для последовательных шагов (алгоритмов)**: Если для пунктов списка порядок 
не важен, для выделения пунктов списка использовать маркеры.
- **Использовать в пунктах списка констукцию "Ключ: Значение."**: 
    - "Ключ" - обобщающая фраза пункта списка, объясняющая суть пункта списка. Обобщающую фразу выделить полужирным 
    начертанием для усиления визуальньного и семантического веса. 
    - Двоеточие - сильный семантический сигнал «определения» или «списочности». Модели обучены воспринимать текст после 
    двоеточия как раскрытие темы до него.
    - Если "Значение" является описанием или правилом, вывод текста начинать с большой буквы, заканчивать точкой. 
    Например, "**Длина пароля**: Не менее 12 символов." 
    - Если "Значение" является параметром, кодом - вывод текста начинать с малькой буквы, не заканчивать точкой. 
    Например, "**Пароль**: сложный". 
    - Конструкция "Ключ: Значение." позволяет:
        - Повысить точность поиска (матчинг заголовка с запросом).
        - Улучшить понимание моделью (четкая связь «свойство — значение»).
        - Сделать текст сканируемым для человека.
        - Помочь чанкеру сохранять логическую целостность блоков.
- **Дублировать рисунки текстом**: RAG-системы (особенно текстовые) не "видят" картинки. Любую важную информацию из 
схем, скриншотов и диаграмм дублировать текстом, например, в подписи или в виде замещающего рисунок описания.
- **Не использовать в тексте статьи базы знаний эмодзи, иконки, декоративные элементы, спецсимволы**: Для надежной, 
предсказуемой и дешевой RAG-системы база знаний должна быть максимально «скучной». Чистый текст, четкая структура 
Markdown, никаких визуальных украшательств. Это гарантирует, что поиск будет работать по смыслу, а не по совпадению 
спецсимволов.
    - Эмодзи в тексте запретить: Использовать обычный текст, жирное начертание.
    - Эмодзи в заголовках запретить: Использовать иерархию #, ## и т.д.
    - Эмодзи в списках запретить: Использовать маркеры -, *, 1.
    - Декоративные картинки, иконки убрать из MD-файлов.
    - Инфографика/схемы	описать текстом: Alt-текст, описание под картинкой. 
    - Визуальные акценты: Использовать MD-форматирование (Цитаты >, блоки кода ```).
- **Отсутствие "мусора" в тексте**: Перед загрузкой статьи в RAG-систему удалить навигационные элементы, футеры, 
которые могут попасть в векторное представление и создать шум при поиске.

## Метаданные (Frontmatter)
Критически важный элемент для управления контекстом и фильтрации. В начале каждого файла рекомендуется использовать YAML 
Frontmatter. 

Метаданные для RAG-системы делятся на три группы: **идентификация** (технические данные), **бизнес-контекст** (смысловые 
данные) и **управление** (жизненный цикл и безопасность). Грамотно заполненные метаданные позволяют реализовать 
пре-фильтрацию поиска, что критически повышает точность ответов.

Заполнение этих полей вручную (или полуавтоматически) при создании базы знаний даст вам мощный инструмент для управления 
качеством поиска и безопасностью данных в RAG-системе.

**Зачем это нужно:**
- **Фильтрация**: Позволяет ограничивать поиск определенными категориями или датами.
- **Контекст**: Поля `title` и `description` могут добавляться к каждому чанку при индексации, чтобы модель понимала, из 
какого документа пришел фрагмент, даже если заголовок был утерян при разбиении.
- **Актуальность**: Поле `last_updated` помогает приоритезировать свежие данные.

### Группа метаданных идентификации

Метаданные группы идентификации обязательны для технической трассировки: чтобы понять, откуда взялся ответ, и избежать 
дублирования:

- Поле document_id:
    - Тип данных: String (UUID)
    - Описание и требования: Уникальный идентификатор исходного файла. Не должен меняться при обновлении версий, если 
    это тот же документ
- Поле chunk_id:
    - Тип данных: String 
    - Описание и требования: Уникальный ID конкретного чанка (фрагмента). Нужен для поиска ошибок и точного цитирования. 
    Присваивается автоматически на этапе загрузки документов в RAG-систему.
- Поле source_uri:
    - Тип данных: String   
    - Описание и требования: Путь к файлу в репозитории или URL. Позволяет пользователю перейти к оригиналу.
- Поле source_system:
    - Тип данных: String  
    - Описание и требования: Название системы-источника (например, «Confluence», «SharePoint», «Manual_v2»). Важно для 
    мультисорсовых баз.
- Поле file_name:
    - Тип данных: String  
    - Описание и требования: Оригинальное имя файла (например, `setup_guide_v3.md`). Полезно для отображения в интерфейсе.
- Поле page_number:
    - Тип данных: Integer   
    - Описание и требования: Если источник — PDF или книга. Для Markdown может быть опущено или заменено на номер секции.

### Группа метаданных бизнес-контекста

Метаданные группы бизнес-контекста самая важная группа для **фильтрации**. Позволяет сузить поиск по запросу 
пользователя (например, «Ищи только для продукта X в отделе Y»).

- Поле title:
    - Тип данных: String    
    - Описание и требования: Заголовок документа или раздела. Должен совпадать с H1 в файле. Критично для сниппетов в выдаче

- Поле topic:
    - Тип данных: String (Enum)   
    - Описание и требования: Основная тема. Требование: используйте контролируемый словарь (тезаурус), чтобы избежать разнобоя.

- Поле department:
    - Тип данных: String (Enum)    
    - Описание и требования: Департамент-владелец (Finance, IT, Sales). Используется для фильтрации по зоне ответственности.

- Поле product:
    - Тип данных: String    
    - Описание и требования: Название продукта или модуля, к которому относится документ. Обязательно для продуктовых баз знаний.

- Поле audience:
    - Тип данных: String (Enum)   
    - Описание и требования: Целевая аудитория: `admin`, `end_user`, `developer`, `manager`. Помогает отсечь сложные технические детали от обычных пользователей.

- Поле language:
    - Тип данных: String (ISO)   
    - Описание и требования: Код языка (например, `ru`, `en`). Обязательно для мультиязычных баз, чтобы модель не смешивала языки.

- Поле region:
    - Тип данных: String 
    - Описание и требования: Географическая привязка (EMEA, NA, Global). Важно для документов с региональными особенностями (законы, налоги).

- Поле keywords:
    - Тип данных: Array[String]
    - Описание и требования: Список тегов. Требование: не более 5–10 тегов на документ. Использовать существительные, а не фразы.

- Поле summary:
    - Тип данных: String 
    - Описание и требования: Краткое описание (1–2 предложения). Может генерироваться LLM автоматически или писаться автором. Помогает при грубом поиске.        

### Группа метаданных управления жизненным циклом (Lifecycle)
Позволяет отсеивать устаревшую информацию и черновики, что напрямую влияет на достоверность ответов.

- Поле version:
    - тип данных: String 
    - описание и требования: Версия документа (например, `1.0`, `2.1-beta`). Помогает приоритезировать свежие данные.

- Поле status:
    - тип данных: String (Enum)
    - описание и требования: Статус зрелости: draft, review, published, archived. Требование: в поиск пускать только published.

- Поле date_published:
    - тип данных:  Date (ISO 8601)
    - описание и требования: Дата публикации. Используется для сортировки "сначала новые".

- Поле last_updated:
    - тип данных: Date (ISO 8601)
    - описание и требования: Дата последнего изменения. Критично для динамических знаний (курсы валют, политики).

- Поле review_date:
    - тип данных: Date (ISO 8601)
    - описание и требования: Дата следующей плановой проверки. Позволяет автоматически помечать документ как "требующий проверки".

- Поле owner:
    - тип данных: String
    - описание и требования: Владелец документа (человек или команда). Нужно для обратной связи и уточнения контента.

### Группа метаданных безопасности и доступа (Security & Governance)

Обязательный блок для корпоративных систем, чтобы RAG не «слил» конфиденциальную информацию не тем пользователям.

- Поле sensitivity_level:
    - тип данных: String (Enum)
    - описание и требования: Уровень чувствительности: public, internal, confidential, restricted. Требование: строгий фильтр перед выдачей.

- Поле access_level:
    - тип данных: String (Enum)
    - описание и требования: Минимальная роль для доступа: guest, user, admin.

- Поле allowed_groups:
    - тип данных: Array[String]
    - описание и требования: Список групп (LDAP/AD), которым разрешен доступ. Например: ["HR_Managers", "IT_Security"].

- Поле tenant_id:
    - тип данных: String 
    - описание и требования: ID тенанта (клиента). Строго обязательно для мульти-тенантных SaaS решений, чтобы данные не пересекались.

### Группа технических метаданных (System)

Заполняются автоматически пайплайном ingestion, но должны быть учтены в схеме.

- Поле ingestion_timestamp:
    - тип данных: Datetime 
    - описание и требования: Время загрузки в базу. Нужно для отладки и инкрементального обновления.

- Поле embedding_model:
    - тип данных: String 
    - описание и требования: Название модели, создавшей вектор (например, text-embedding-3-large). Нужно, если 
    планируется менять модели и делать ре-индексацию.

- Поле chunk_index:
    - тип данных: Integer 
    - описание и требования: Порядковый номер чанка в документе (1 из 5). Полезно для восстановления последовательности.

- Поле token_count:
    - тип данных: Integer 
    - описание и требования: Количество токенов в чанке. Нужно для контроля лимитов контекстного окна.

### Практические требования к реализации

1. **Схема должна быть плоской**: Избегать вложенных JSON-объектов внутри метаданных. Использовать плоские ключи: 
product_name, product_version вместо product: {name, version}. 
2. **Типизация данных**: Строго соблюдать типы. Даты — только в формате ISO 8601 (2026-09-29T10:30:00Z), числа — без 
кавычек. Ошибки типов могут сломать фильтрацию.
3. **Контролируемые словари (Taxonomy)**: Для полей status, department, sensitivity_level использовать строго заданные 
значения (Enum). Не допускать вариативности ("Опубликовано" vs published), иначе фильтрация не сработает.
4. **Обязательные поля (Required)**: Определить минимальный набор, без которого документ не принимается в базу. Обычно 
это: document_id, title, status, sensitivity_level.

## Стратегия чанкинга (разбиения)

Архитектура файлов должна учитывать, как текст будет разбиваться на части для векторной базы данных.

- **Оптимальный размер**: Рекомендуемый размер чанка для общих знаний — 600–1000 токенов. Для сложного технического 
контента — меньше (100–200 токенов).
- **Перекрытие (Overlap)**: Обязательно предусмотреть перекрытие между чанками (10–20% от размера чанка, например, 
80–160 токенов). Это сохраняет связность текста на стыках разделов.
- **Границы по заголовкам**: Алгоритм чанкинга должен учитывать иерархию заголовков, не разрывая разделы статьи 
посередине, если они меньше лимита токенов.




## 4. Оптимизация под сценарии использования

Адаптируйте контент под то, как пользователи будут задавать вопросы.

* **Формат «Вопрос — Ответ»**: Включайте в текст явные вопросы, которые могут возникнуть у пользователя, и сразу давайте на них ответы. Это создает идеальные паттерны для retrieval.
    * *Пример*: «**Как сбросить пароль администратора?** Для сброса пароля выполните команду...».[1][5]
* **Сценарии (Session Starters)**: Для сложных процедур добавляйте вводный блок «Когда это использовать». Это помогает системе отсечь нерелевантные инструкции, если пользователь спрашивает о другом сценарии.[1]
* **Тестирование на реальных вопросах**:
    1. Соберите 10–20 реальных вопросов пользователей.
    2. Попробуйте найти ответы в вашей БЗ вручную или через прототип RAG.
    3. Если ответ не находится или неполный — перепишите соответствующий раздел, добавив недостающие ключевые слова и контекст.[9][10]

## 5. Чек-лист качества документа

Перед загрузкой файла в базу проверьте его по этим пунктам:

1. [ ] **Заголовок H1** уникален и точно описывает содержание.
2. [ ] **Метаданные** (Frontmatter) заполнены (категория, теги).
3. [ ] **Нет «висячих» местоимений** (понятно ли, что такое «он» в отрыве от контекста?).
4. [ ] **Таблицы заменены** на списки или описательный текст.
5. [ ] **Картинки описаны** текстом (важная информация не только на изображении).
6. [ ] **Разделы самодостаточны** (можно читать любой раздел без обязательного чтения введения).
7. [ ] **Ключевые слова** из запросов пользователей встречаются в заголовках и первых предложениях.[4][6][8]

Чек-лист автора перед сохранением файла:
1. Заголовок # ровно один и стоит на первой строке (после метаданных).
2. Все ссылки на другие файлы БЗ оформлены как [Текст](../путь/файл.md).
3. В тексте нет ссылок на локальный диск C://Users/....
4. Списки оформлены через *, а не через дефисы в строчку.
5. Заполнен блок метаданных в начале файла.


Соблюдение этих правил превратит вашу базу знаний из простого хранилища файлов в оптимизированный датасет, который обеспечит высокую точность и релевантность ответов RAG-системы.
