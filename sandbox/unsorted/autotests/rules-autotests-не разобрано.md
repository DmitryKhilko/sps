# ChatGPT
## Анализ информации, предложенной мной
Дима, я внимательно разобрал документ именно как набор рекомендаций, а не как будущий обязательный регламент. В таком качестве он уже довольно сильный: здесь есть пирамида тестирования, распределение ответственности между слоями, независимость автотестов от кода приложения, тестовые данные, API/UI, инфраструктура, CI/CD, flaky, баг-репорты, Grafana и сопровождение. 
Но если смотреть на документ как на целостную методологию построения системы функциональной автоматизации, то я вижу несколько важных пробелов.

1. Самый существенный пробел — нет жизненного цикла самого автотеста
Сейчас хорошо описано, как создать автотест, но практически не описано, что с ним происходит дальше.
Я бы добавил отдельный раздел:
«Жизненный цикл автотеста»
Например:

Требование → чек-лист → решение о необходимости автоматизации → разработка → code review → первый запуск → включение в набор → CI → сопровождение → изменение → deprecated → удаление.

Для каждого автотеста желательно иметь состояние:
Proposed
In Development
Ready
Active
Flaky
Quarantined
Deprecated
Removed

Это особенно важно, потому что у тебя уже есть идея карантина flaky-тестов, но нет полного управления жизненным циклом. Сейчас описано, что flaky-тест надо вывести из blocking pipeline и отправить в техдолг, но не определено, когда и как он возвращается обратно. 

---

2. Не хватает определения: «что вообще автоматизировать?»
Есть ранжирование функционала по критичности. 
Но критичность — не единственный критерий.
Я бы добавил матрицу целесообразности автоматизации.
Например:

Критерий Вопрос

Критичность Что будет, если функция сломается?
Частота Как часто функция используется?
Регрессионность Может ли она сломаться вследствие изменений в другом месте?
Стабильность Функциональность уже устоялась?
Стоимость ручной проверки Сколько времени занимает ручная проверка?
Частота прогона Как часто этот тест понадобится запускать?
Стоимость автоматизации Сколько стоит создание/поддержка теста?
Сложность автоматизации Насколько сложно автоматизировать?
Диагностируемость Можно ли будет понять причину падения?
ROI Окупится ли автоматизация?


То есть решение:

> «Автоматизировать / не автоматизировать / автоматизировать позже»
должно быть отдельным инженерным решением.

---

3. Нет понятия «тестовый сценарий» против «проверки»

Это важный момент.
Например:
Тест: Создание партнёрства
может содержать:
1. авторизация;
2. открытие формы;
3. заполнение;
4. отправка;
5. проверка HTTP 201;
6. проверка данных;
7. проверка записи в БД;
8. проверка события;
9. проверка файла.

Но тогда возникает вопрос:

> Что считать одним автотестом?

Это сильно влияет на метрики.

Я бы добавил рекомендации по гранулярности автотестов:

один тест = одна бизнес-проверка;
не превращать тест в огромный сценарий из 30 проверок;
не дробить очевидно связанные проверки чрезмерно;
E2E допускает сценарии;
компонентный тест предпочтительно атомарен.

У тебя атомарность уже упоминается для CRUD-тестов. Но критерии атомарности пока не определены.

---

4. Не хватает явного разделения «проверяемого результата» и «технических деталей»

Это особенно важно для твоей идеи независимого «цифрового ОТК».
Я бы ввёл структуру:

Business expectation → Test condition → Action → Expected result → Technical verification.

Например:

> При создании партнёрства с корректными данными партнёрство должно быть создано.



А уже ниже:

HTTP 201;

id != null;

запись появилась в БД;

событие опубликовано;

статус ACTIVE.


Это позволяет не превращать автотест в набор технических assertions.

Твой документ очень хорошо говорит, что автотест должен проверять требования BA, а не текущее поведение кода. 

Но я бы формализовал эту мысль.

5. Не хватает Traceability Matrix

У тебя уже есть замечательная основа:

> чек-лист имеет уникальный ID → автотест обязан содержать этот ID. 



Но это пока только связь:

Checklist → Automated Test

А я бы расширил:

Requirement → Checklist → Test → Test Run → Defect

Например:

Dmitry:
FR-PARTNER-001
↓
CL-PARTNER-API-001
↓
test_create_partner_valid()
↓
Run #1542 — FAILED
↓
BUG-4821

И обратное направление:

> Для какого требования был создан этот тест?



Это даст полноценную трассируемость качества.

6. Нет рекомендации по контролю «потерянных» требований

Requirement Coverage

Не просто:

> 850 автотестов.



А:

> 87% требований имеют автоматизированные проверки.



И отдельно:

требования без тестов;

требования только с ручными проверками;

требования только с API;

требования только с UI;

критические требования без E2E;

устаревшие тесты для удалённых требований.


Это очень хорошо ложится на твою существующую идею вертикального покрытия бизнес-функциональности.

7. Нет Test Data Management как отдельной подсистемы

У тебя генерация данных описана очень подробно — boundary, equivalence classes, JSON Schema и т. д. 
Но отсутствуют:
Управление состоянием тестовых данных
Например:
создание;
получение;
изменение;
очистка;
восстановление;
уникальность;
TTL;
изоляция;
зависимости между сущностями.

Особенно важно определить:
> Может ли тест изменять общие данные?



Лучше рекомендовать:
Test creates → Test uses → Test cleans
либо использовать уникальный namespace/test-run ID.

8. Не хватает изоляции параллельных тестов

Ты рекомендуешь parallel execution. 
Но параллельный запуск без стратегии изоляции данных очень быстро превращается в источник flaky.

Я бы добавил:
«Правила параллельного выполнения»
Тесты не должны конфликтовать:
Test A → partner_123
Test B → partner_456

а не:

Test A ─┐
├→ partner_123
Test B ─┘

Нужно определить:

уникальные данные;

namespace;

test-run ID;

отдельные БД/схемы при необходимости;

блокировки;

зависимости;

serial tests.

9. Не хватает принципа идемпотентности

Очень полезное правило:

> Повторный запуск одного теста не должен зависеть от предыдущего запуска.



Например:

pytest test_create_partner
pytest test_create_partner
pytest test_create_partner

должны работать независимо друг от друга.

Это особенно важно для CRUD.

10. Не хватает правил очистки тестовых данных

Сейчас говорится, что тест может подготовить окружение. 

Но отсутствует обратная сторона:

> Кто удаляет созданные данные?



Я бы рекомендовал рассмотреть три стратегии:

A. Cleanup после теста

Act

B. Cleanup перед тестом

Всё окружение уничтожается после тестового запуска.

Это стоит выделить отдельно.

24. Нет mutation testing

Это уже более продвинутый уровень, но как рекомендация я бы добавил.

Идея:

> Искусственно изменить код приложения и проверить, способен ли тест это обнаружить.



Например:

if amount > 1000:

заменить на:

if amount >= 1000:

Если тесты продолжают проходить — значит, соответствующая проверка недостаточно сильная.

Это отличный способ оценивать качество тестов, а не просто их количество.

> Risk Coverage — покрытие наиболее опасных сценариев.

❌ тест отключён без задачи на исправление
❌ hardcoded IDs
❌ привязка к тексту UI без необходимости.

34. Не хватает «Definition of Done» для автотеста

Очень полезно сделать небольшой чек-лист:

Автотест считается готовым, если:

есть связь с требованием/чек-листом;

определён уровень пирамиды;

тест независим;

данные изолированы;

нет sleep;

есть необходимые assertions;

есть диагностика;

тест проходит локально;

проходит в CI;

добавлены необходимые tags;

code review пройден;

тест включён в соответствующий набор;

результат отображается в отчёте.


Это не регламент, а рекомендуемый DoD.

Моя главная оценка

Самое сильное место твоего документа — принцип независимости автотестов от реализации приложения. Ты прямо фиксируешь, что автотест должен быть «цифровым ОТК» и проверять соответствие требованиям, а не воспроизводить внутреннюю реализацию кода. 

А вот чего пока не хватает концептуально — это управления системой автотестов как отдельным продуктом.

Сейчас документ в основном отвечает на вопрос:

ДОПОЛНИТЕЛЬНЫЕ РЕКОМЕНДАЦИИ ПО СОЗДАНИЮ ФУНКЦИОНАЛЬНЫХ АВТОТЕСТОВ

🟦 [АЛЬТУС] 1. Жизненный цикл функционального автотеста
При создании функционального автотеста рекомендуется учитывать его полный жизненный цикл:
1. определение необходимости автоматизации проверки;
2. определение функциональности и сценария, который необходимо проверить;
3. определение предусловий и тестовых данных;
4. разработка автотеста;
5. код-ревью;
6. первый запуск и устранение ошибок;
7. включение автотеста в соответствующий набор тестов;
8. выполнение автотеста в CI/CD;
9. анализ результатов выполнения;
10. сопровождение автотеста при изменении функциональности;
11. вывод автотеста из эксплуатации при утрате его актуальности.

Автотест не должен рассматриваться как законченный только после написания программного кода.
Результатом создания автотеста является рабочая проверка, которая может быть воспроизведена, диагностирована, включена в соответствующий тестовый набор и поддерживаться в актуальном состоянии.

---

🟦 [АЛЬТУС] 2. Критерии выбора функциональности для автоматизации
Перед созданием автотеста рекомендуется определить целесообразность автоматизации проверки.
В первую очередь рекомендуется автоматизировать проверки, которые:
выполняются регулярно;
входят в регрессионное тестирование;
относятся к критически важной функциональности;
имеют высокую стоимость ручного выполнения;
требуют большого количества повторяющихся действий;
имеют стабильные ожидаемые результаты;
связаны с большим количеством комбинаций входных данных;
должны выполняться после каждого изменения системы;
позволяют быстро обнаружить дефект;
имеют высокий риск возникновения дефектов.

Не рекомендуется автоматически переносить в автотесты все существующие ручные проверки.
Автоматизация должна обеспечивать снижение трудозатрат на проверку и повышение качества контроля, а не приводить к созданию большого количества малоценных или дорогостоящих в сопровождении автотестов.

---

🟦 [АЛЬТУС] 3. Гранулярность функционального автотеста
Один автотест рекомендуется использовать для проверки одного логически законченного сценария или одного набора тесно связанных проверок.
Не рекомендуется создавать чрезмерно большие автотесты, содержащие большое количество независимых действий и проверок.
При возникновении ошибки автотеста должно быть возможно однозначно определить:
какой сценарий выполнялся;
на каком этапе произошла ошибка;
какое условие не выполнено;
какие входные данные использовались;
какое ожидаемое и фактическое состояние получено.

---

🟦 [АЛЬТУС] 4. Трассируемость проверок
Для каждого функционального автотеста рекомендуется обеспечивать возможность определить его связь с проверяемой функциональностью.
Рекомендуемая цепочка трассируемости:
Требование → Чек-лист → Автотест → Запуск → Результат → Дефект.
Автотест должен иметь идентификатор или набор меток, позволяющих установить:
какую функциональность он проверяет;
к какому требованию относится;
какой пункт чек-листа автоматизирован;
к какому набору тестов относится;
в каких запусках выполнялся;
какие дефекты выявлял.

Трассируемость рекомендуется использовать не только для отчетности, но и для анализа полноты покрытия требований.

---

🟦 [АЛЬТУС] 5. Виды покрытия функциональности
При оценке автоматизации рекомендуется различать несколько видов покрытия.
Покрытие требований
Показывает, какая часть требований имеет соответствующие проверки.
Покрытие функциональности
Показывает, какие функциональные возможности системы проверяются автотестами.
Покрытие рисков
Показывает, насколько автоматизированы проверки функциональности с высоким риском возникновения или высокой стоимостью дефекта.
Покрытие сценариев
Показывает, какие пользовательские и бизнес-сценарии имеют автоматизированные проверки.
Высокое количество автотестов само по себе не означает высокое качество покрытия.

---

🟦 [АЛЬТУС] 6. Проверка состояний системы
Для функциональности, поведение которой зависит от состояния объекта, рекомендуется использовать проверки переходов между состояниями.
При разработке автотестов рекомендуется учитывать:
допустимые переходы;
недопустимые переходы;
начальное состояние;
конечное состояние;
условия перехода;
действия пользователя или системы, вызывающие переход;
попытки выполнения операций в неподходящем состоянии.

Особое внимание рекомендуется уделять проверке невозможности выполнения запрещенных операций.

---

🟦 [АЛЬТУС] 7. Проверка комбинаций условий
Если результат выполнения операции зависит от нескольких условий, рекомендуется использовать подход на основе таблицы решений.
Для таких сценариев необходимо определить:
набор условий;
возможные значения условий;
комбинации условий;
ожидаемый результат для каждой значимой комбинации.

Не рекомендуется ограничиваться проверкой отдельных условий независимо друг от друга, если дефект может возникнуть именно при их совместном выполнении.

---

🟦 [АЛЬТУС] 8. Негативные бизнес-сценарии
Негативные проверки рекомендуется выполнять не только для проверки валидации отдельных полей.
Необходимо также проверять ситуации, когда пользователь выполняет недопустимое бизнес-действие.
Например:
выполнение операции в запрещенном состоянии;
повторное выполнение уже выполненной операции;
отсутствие необходимых связанных данных;
нарушение бизнес-ограничений;
попытка выполнения операции пользователем без соответствующих полномочий;
использование объекта, который уже был изменен или удален;
выполнение операций в неправильной последовательности.

Автотест должен проверять не только то, что система принимает корректные данные, но и то, что система предотвращает выполнение недопустимых операций.

---

🟦 [АЛЬТУС] 9. Тестовые данные
Тестовые данные должны создаваться таким образом, чтобы автотест мог быть воспроизведен независимо от предыдущих запусков.
Рекомендуется:
минимизировать зависимость тестов друг от друга;
создавать необходимые данные непосредственно в рамках теста либо предусматривать надежный механизм подготовки;
использовать уникальные идентификаторы для объектов;
удалять или переводить в необходимое состояние созданные данные после выполнения;
избегать использования общих данных, которые могут изменяться другими тестами;
предусматривать возможность повторного запуска теста.

---

🟦 [АЛЬТУС] 10. Независимость и идемпотентность автотестов
Автотест рекомендуется проектировать таким образом, чтобы его повторный запуск при одинаковых условиях приводил к одинаковому ожидаемому результату.
Не рекомендуется создавать зависимость вида:
Тест №2 выполняется только после успешного выполнения теста №1.
Если несколько тестов используют один объект, изменение состояния этого объекта одним тестом не должно приводить к непредсказуемому результату другого теста.

---

🟦 [АЛЬТУС] 11. Параллельное выполнение
При возможности параллельного выполнения необходимо учитывать влияние тестов друг на друга.
Автотесты не должны:
использовать одни и те же изменяемые данные без необходимости;
изменять общие настройки системы;
зависеть от порядка выполнения;
использовать общие временные файлы или ресурсы без изоляции;
изменять состояние другого теста.

При необходимости должны использоваться механизмы изоляции тестовых данных и окружения.

---

🟦 [АЛЬТУС] 12. Проверка асинхронных операций
Для операций, результат которых появляется не сразу, рекомендуется предусматривать ожидание ожидаемого состояния, а не фиксированную задержку.
Не рекомендуется использовать без необходимости конструкции вида:
ожидание N секунд → проверка результата.
Предпочтительно ожидать конкретное условие:
появление объекта;
изменение статуса;
завершение операции;
появление сообщения;
изменение значения;
завершение обработки системой.

Время ожидания должно иметь ограничение, после которого тест завершается с диагностической информацией.

---

🟦 [АЛЬТУС] 13. Диагностика ошибок
При падении автотеста необходимо обеспечить достаточное количество информации для определения причины ошибки.
В зависимости от типа проверки рекомендуется сохранять:
входные параметры;
идентификаторы объектов;
HTTP-запрос и ответ;
статус-код;
текст ошибки;
состояние объекта;
скриншот;
видео;
trace;
логи;
Correlation ID / Trace ID;
информацию о версии приложения;
информацию об окружении.

Диагностические данные должны позволять по возможности воспроизвести проблему без повторного запуска теста.

---

🟦 [АЛЬТУС] 14. Correlation ID / Trace ID
Для интеграционных и распределенных систем рекомендуется сохранять идентификатор запроса или операции, позволяющий найти соответствующие записи в логах различных компонентов системы.
При падении теста рекомендуется выводить данный идентификатор в отчет.
Это позволяет связать:
Автотест → запрос → сервис → лог → ошибка.

---

🟦 [АЛЬТУС] 15. Авторизация и права доступа
Функциональные автотесты должны учитывать не только успешное выполнение операции авторизованным пользователем, но и ограничения доступа.
Для критичных операций рекомендуется проверять:
доступ пользователя с необходимыми правами;
отсутствие доступа пользователя без необходимых прав;
доступ к разрешенным объектам;
запрет доступа к запрещенным объектам;
выполнение операций в зависимости от роли;
изменение доступности операции после изменения роли или состояния пользователя.

---

🟦 [АЛЬТУС] 16. Интеграционные ошибки

При наличии взаимодействия нескольких компонентов рекомендуется проверять не только успешный обмен данными.
Следует предусматривать сценарии:
недоступности внешнего сервиса;
получения некорректного ответа;
превышения времени ожидания;
повторного получения сообщения;
получения сообщения с неизвестным идентификатором;
нарушения формата данных;
отсутствия обязательных данных;
повторной отправки запроса.

Ожидаемое поведение системы при ошибке интеграции должно быть явно определено.

---

🟦 [АЛЬТУС] 17. Политика повторных попыток
Повторный запуск операции или теста должен использоваться только там, где это обосновано.
Не рекомендуется использовать безусловные повторные попытки для скрытия нестабильности тестов.
Для повторных попыток необходимо определить:
количество попыток;
интервал между попытками;
типы ошибок, при которых повтор разрешен;
типы ошибок, при которых повтор запрещен;
максимальное общее время ожидания.

Повторная попытка не должна маскировать реальный дефект приложения.

---

🟦 [АЛЬТУС] 18. Классификация результатов автотестов
При анализе падений рекомендуется разделять причины неуспешного выполнения.
Минимально рекомендуется выделять:
дефект приложения;
ошибка тестовых данных;
ошибка автотеста;
ошибка тестового окружения;
ошибка внешней системы;
проблема инфраструктуры;
временная нестабильность;
неизвестная причина.

Количество падений автотестов без классификации причин не позволяет объективно оценить качество продукта.

---

🟦 [АЛЬТУС] 19. Стабильность автотестов
Автотест, который периодически завершается ошибкой при неизменном состоянии системы, считается нестабильным.
Для нестабильных тестов рекомендуется:
1. зарегистрировать проблему;
2. определить причину нестабильности;
3. исправить автотест или причину в окружении;
4. повторно проверить стабильность;
5. вернуть тест в основной набор.

Не рекомендуется длительное время оставлять нестабильные тесты в основном регрессионном наборе без обозначения их состояния.

---

🟦 [АЛЬТУС] 20. Наборы функциональных автотестов
Рекомендуется использовать классификацию автотестов по назначению.
Например:
Smoke — минимальный набор для проверки работоспособности системы;
Critical — проверки наиболее критичных функций;
Changed Area — проверки функциональности, затронутой изменениями;
Regression — основной регрессионный набор;
Release — проверки перед выпуском версии;
Full — полный набор доступных функциональных автотестов.

Каждый набор должен иметь понятное назначение и критерии включения тестов.

---

🟦 [АЛЬТУС] 21. Выбор набора тестов при изменении системы
При изменении функциональности рекомендуется определять набор автотестов, которые необходимо выполнить в зависимости от области изменений.
Для этого может использоваться связь:
Изменение → функциональность → требования → автотесты.
Для небольших изменений не всегда необходимо выполнять полный набор тестов, если существует надежный механизм определения затронутой функциональности.
При этом перед выпуском версии должен выполняться установленный регрессионный или release-набор.

---

🟦 [АЛЬТУС] 22. Качество кода автотестов
Код автотестов должен соответствовать общим требованиям к качеству программного кода.
Рекомендуется контролировать:
читаемость;
отсутствие дублирования;
понятность имен;
размер методов;
корректное использование фикстур;
отсутствие скрытых зависимостей;
обработку ошибок;
повторное использование общего кода;
структуру Page Object / API-клиентов;
отсутствие захардкоженных данных там, где они не нужны.

Автотесты должны быть понятны другому разработчику или тестировщику, который будет их сопровождать.

---

🟦 [АЛЬТУС] 23. Антипаттерны функциональных автотестов
Не рекомендуется использовать следующие подходы:
один тест проверяет большое количество независимых сценариев;
тест зависит от результата другого теста;
использование фиксированных задержек вместо ожидания состояния;
использование общих изменяемых тестовых данных;
большое количество дублирующегося кода;
проверки внутренних деталей реализации вместо функционального поведения;
чрезмерное количество технических проверок;
игнорирование ошибок теста посредством большого количества retry;
отключение теста без указания причины;
копирование одного и того же теста для разных данных без параметризации;
отсутствие диагностической информации при падении.

---

🟦 [АЛЬТУС] 24. Definition of Done для функционального автотеста
Функциональный автотест рекомендуется считать завершенным, если:
определена проверяемая функциональность;
определен ожидаемый результат;
определены предусловия;
определены тестовые данные;
реализована необходимая проверка;
автотест воспроизводим;
автотест не зависит от порядка выполнения других тестов;
предусмотрена диагностика ошибки;
определен набор, в который включается автотест;
выполнено код-ревью;
автотест успешно выполняется в целевом окружении;
обеспечена связь с соответствующим требованием или пунктом чек-листа.

---

🟦 [АЛЬТУС] 25. Работа с дефектами, обнаруженными в эксплуатации
Если дефект был обнаружен после передачи функциональности пользователям, рекомендуется определить возможность создания автоматической проверки, предотвращающей повторное появление дефекта.
Для значимых дефектов рекомендуется создавать автотест, который:
1. воспроизводит исходную ошибочную ситуацию;
2. фиксирует некорректное поведение;
3. после исправления подтверждает корректное поведение;
4. включается в соответствующий регрессионный набор.

Таким образом, каждый существенный исправленный дефект может становиться дополнительной защитой от регрессии.

---

🟦 [АЛЬТУС] 26. Test Debt
При разработке функциональности может возникать задолженность по автоматизации тестирования.
Test Debt рекомендуется фиксировать в случаях, когда:
ручная проверка существует, но автоматизация признана необходимой;
автотест временно невозможно создать;
часть сценариев функциональности не автоматизирована;
существующий автотест требует переработки;
тест временно отключен;
отсутствуют необходимые средства для автоматизации.

Test Debt необходимо периодически анализировать и планировать его устранение.

---

🟦 [АЛЬТУС] 27. Устаревшие автотесты
При изменении функциональности необходимо проверять актуальность существующих автотестов.
Если проверяемая функциональность была удалена или существенно изменена, соответствующий автотест должен быть:
изменен;
заменен;
объединен с другим тестом;
либо удален.

### 1. Специфика EDI и Асинхронных процессов 🟥
В EDI-системах много асинхронной логики (очереди, обмен XML-файлами с внешними контрагентами, банками, госорганами). Текущий документ фокусируется на синхронных API и UI.
* Тестирование очередей и асинхронности: Необходимо описать, как тестировать фоновые задачи (например, RabbitMQ, Kafka, Celery). Как автотест понимает, что документ не просто сохранен в БД, но и успешно ушел в очередь, был обработан воркером и сгенерировал ответный XML?
* Мокирование (Stubbing) внешних систем: EDI-Flow взаимодействует с внешним миром. В рекомендациях нужно закрепить правило: никаких обращений к реальным внешним API (банки, провайдеры ЭДО) в функциональных тестах. Рекомендуется использовать инструменты мокирования (WireMock, Mountebank) или встроенные моки фреймворка, чтобы эмулировать ответы внешних систем (включая таймауты и 500-е ошибки от внешних партнеров).
* Валидация XML/XSD: Упомянуть, что генерация и парсинг XML должны проверяться не только на "наличие тегов", но и на строгое соответствие XSD-схемам, утвержденным бизнесом/стандартами (например, УНП, форматы дат в специфичных тегах).

### 2. Трассируемость и Observability (Наблюдаемость) 🟨
Когда падает E2E-тест в микросервисной архитектуре, поиск причины может занять часы.
* Сквозные Correlation ID / Request ID: 🟥 Внедрить правило: каждый API-запрос из автотеста должен генерировать и передавать уникальный X-Request-Id (или X-Correlation-Id). При падении теста в баг-репорте автоматически должен подставляться этот ID, чтобы QA/Dev мог за 1 секунду выгрузить все логи по этому запросу из Grafana/Kibana/ELK.
* Проверка логов приложения: 🟩 В интеграционных тестах полезно добавить шаг, который через API лог-сервера (или напрямую читая логи контейнера) проверяет, что приложение не просто вернуло 200 OK, но и не написало ERROR / Exception в свои внутренние логи (например, скрытые NullPointerException).

### 3. Безопасность и Матрица доступов (RBAC) 🟥
В документе упомянуты роли, но нет подхода к тестированию безопасности.
* Тестирование матрицы доступов (RBAC): 🟥 Необходимо автоматизировать проверку горизонтального и вертикального разграничения доступа. (Например: Пользователь А не может прочитать API-ручку GET /api/documents/{id}, если документ принадлежит Пользователю Б — защита от IDOR).
* Проверка утечек данных в ответах: 🟩 Убедиться, что API не возвращает в JSON-ответах чувствительные данные (пароли, токены, полные номера карт/паспортов), даже если они есть в БД.

### 4. Управление тестовыми данными при Параллельном запуске 🟥
Вы верно рекомендуете параллельный запуск и Testcontainers. Но это несет риски.
* Изоляция данных (Data Isolation): 🟥 Если тесты идут в параллель и используют одну БД (или даже разные, но с общими справочниками), нужно избежать гонок (race conditions). Рекомендуется использовать уникальные префиксы для тестовых сущностей (например, test_user_{uuid}) или паттерн "Tenant per test".
* Очистка данных (Teardown): 🟨 Если тесты не используют изолированные контейнеры на каждый тест (а используют beforeAll), необходимо прописать стратегию очистки (Teardown) данных после прогона набора, чтобы "мусор" не накапливался и не ломал последующие билды.

1. 🟥 Каждый компонентный интеграционный и E2E-автотест обязан самостоятельно подготавливать и очищать необходимые ему данные. Запрещено полагаться на данные, оставленные предыдущими тестами.

## Дополнения к разделу "Описание рекомендуемой структуры автотестов"
1. 🟥 Уровень 2.3. Тестирование асинхронных процессов и очередей сообщений (Message Brokers)
- Тип: Интеграционные тесты очередей (RabbitMQ / Kafka / ActiveMQ).
- Проверяют:
- Корректность маршрутизации, сериализации/десериализации сообщений и обработки задержек (Dead Letter Queues).
- В EDI-системах обмен документами часто асинхронен. Тесты должны уметь отправлять событие в шину, ожидать появления сообщения в очереди-потребителе и проверять его payload.
2. 🟨 Уровень 2.4. Контрактное тестирование (Contract Testing) для внешних систем
- Тип: Тесты контрактов (например, с использованием Pact).
- Проверяют:
- Совместимость API EDI-Flow с API внешних контрагентов или государственных систем (например, ЭДО-операторов, ГИС).
- Позволяет зафиксировать ожидания от внешнего API и гарантировать, что его обновления не сломают интеграцию.

## Дополнения к разделу "Рекомендуемая архитектура автотестов"
### Общие рекомендации
1. 🟥 Запрет на "маскировку" багов с помощью автоматических повторных запусков (Smart Retries)
- В автотестах запрещено оборачивать проверки бизнес-логики (assert) в циклы повторных попыток (retry).
- Разрешены "умные ретраи" (Smart Retries) исключительно на уровне сетевых вызовов (HTTP-запросы, подключение к БД) для нивелирования эффектов "мигающей" сети или перезапуска подов в Kubernetes. Если API вернул 500 или 400 — тест обязан упасть сразу.
2. 🟨 Абстракция API-клиента (API Client Wrapper)
- Рекомендуется не писать requests.post/get напрямую в теле каждого теста.
- Необходимо создать слой API-клиентов (классы-обертки), которые инкапсулируют логику формирования URL, заголовков, авторизации и базовой обработки ответов. Тест должен вызывать метод client.create_document(payload), а не заниматься "сетевой магией".

### UI-автотесты
1. 🟥 Использование паттерна Page Components (или Page Object)
- Несмотря на то, что читаемость важнее слепого DRY, код UI-тестов обязан быть структурирован.
- Локаторы и методы взаимодействия с повторяющимися элементами (таблицы, модальные окна, хедеры, сайдбары) должны быть вынесены в отдельные компоненты/классы. Это позволит при изменении верстки (например, смены id кнопки "Сохранить") исправить локатор в одном месте, а не в 50 тестах.

## Новый раздел: "Специфика тестирования EDI-систем"
1. 🟥 Мокирование внешних EDI-шлюзов и контрагентов
- Тестовая среда не должна зависеть от доступности внешних сервисов (например, тестовых контуров внешних ЭДО-операторов).
- Рекомендуется использовать инструменты мокирования (например, WireMock или Mountebank) для эмуляции ответов внешних систем. Моки должны настраиваться динамически из кода автотеста (через API самого WireMock) под конкретный сценарий.
2. 🟥 Строгая валидация XML и XSD-схем
- Поскольку EDI-Flow работает с документооборотом, генерация и парсинг XML являются критичными.
- В API-автотестах, проверяющих формирование исходящих документов, обязательно использовать валидацию по XSD-схемам (например, библиотеки lxml в Python). Ошибка валидации XML должна трактоваться как критический баг приложения.

Dmitry:
3. 🟨 Тестирование "грязных" и невалидных XML-документов
- Необходимо покрывать тестами сценарии, когда внешняя система присылает malformed XML, XML с нарушенной кодировкой или документы, не соответствующие бизнес-схеме. Система должна корректно обрабатывать такие ошибки, не "падая" с 500 Internal Server Error, а возвращая понятный статус ошибки и сохраняя инцидент в логи/БД.

## Дополнения к разделу "Рекомендуемая инфраструктура автотестов"
1. 🟨 Кэширование зависимостей и Docker-образов в CI/CD
- Для ускорения пайплайнов необходимо настроить кэширование pip/npm зависимостей и слоев Docker-образов (Docker Layer Caching) на уровне CI-сервера. Это сократит время подготовки тестового окружения (setup phase) с минут до секунд.
2. 🟨 Интеграция с мессенджерами (Telegram / Slack / Teams)
- Рекомендуется настроить автоматическую отправку сводок (алертов) в профильные чаты команд.
- Формат алерта: статус прогона (Успех/Падение), ссылка на дашборд Grafana, ссылка на артефакты/логи, список упавших тестов и тег ответственного (если удалось определить по git blame или владельцу модуля).

## Новый раздел: "Нефункциональное тестирование в CI/CD"
1. 🟩 Базовое нагрузочное тестирование (Performance / Load)
- Для критичных API (например, массовая загрузка документов, выгрузка реестров) рекомендуется создать набор скриптов (например, на k6 или JMeter).
- Эти скрипты должны запускаться в CI еженightly (ночью) или перед крупными релизами для контроля деградации производительности (time response не должен расти от билда к билду).
2. 🟩 Автоматизированный Security-скан (DAST)
- Рекомендуется интегрировать в CI-конвейер (на этапе деплоя на QA-стенд) запуск базового сканера уязвимостей (например, OWASP ZAP).
- Сканер должен проверять наличие базовых уязвимостей (XSS, SQL-инъекции, отсутствие заголовков безопасности, CORS-политики) и блокировать релиз при нахождении уязвимостей уровня High/Critical.

## Дополнения к разделу "Сопровождение автотестов"
1. 🟨 Регулярный "Test Gardening" (Садовничество / Рефакторинг тестов)
- Тестовый код стареет и обрастает "костылями" так же быстро, как и основной код.
- Рекомендуется выделять 10-15% времени каждого спринта на рефакторинг автотестов: удаление дублирующего кода, обновление устаревших паттернов, чистку "мертвых" тестов, которые проверяют удаленный функционал, но всё еще числятся в чек-листах.
2. 🟥 Жизненный цикл тестовых данных (Data Teardown)
- Если автотест создает сущности в БД или файлы в MinIO, он обязан их удалять после завершения прогона (в блоке teardown / afterAll), даже если тест упал.
- Исключение: если тест помечен как @debug и запущен локально разработчиком. В CI "мусор" в БД и MinIO должен уничтожаться, чтобы не переполнять тестовые контуры и не ломать последующие прогоны.

Он охватывает пирамиду тестирования, независимость тестового фреймворка, генерацию данных на основе JSON-схем/OpenAPI, контейнеризацию в RAM (tmpfs), а также отчетность в Grafana и правила обработки flaky-тестов.

# ДОПОЛНЕНИЯ К ПРАВИЛАМ СОЗДАНИЯ ФУНКЦИОНАЛЬНЫХ АВТОТЕСТОВ
## Интеграция с СУБД, миграции и состояние БД
1. 🟥 Проверка миграций базы данных (Alembic/Flyway)
* В концепцию использования Testcontainers необходимо добавить обязательный запуск миграций «с нуля» до текущей версии схемы перед началом прогона интеграционных/CRUD-тестов.
* *Зачем:* проверка, что свежие миграции накатываются без ошибок на пустую БД и не ломают совместимость со схемами.
2. 🟨 Стратегия очистки тестовых данных (TearDown / Isolation)
* Для интеграционных API-тестов, запускаемых в одной сессии DB, должна быть определена стратегия изоляции: транзакционный rollback после каждого теста или использование библиотек чистки (например, database_cleaner / явный truncate пользовательских таблиц).
* *Зачем:* исключить взаимное влияние тестов друг на друга (Side Effects) при параллельном прогоне в рамках одного контейнера/схемы.
3. 🟩 Служба отслеживания "висячих" процессов и утечек соединений
* Убедиться, что тесты корректно закрывают пул соединений к PostgreSQL/DB при завершении работы и при нештатном прерывании (SIGINT/SIGTERM).

## Особенности тестирования асинхронных процессов и очередей
1. 🟥 Тестирование асинхронных задач (Celery / RabbitMQ / Redis)
* Для сценариев EDI-Flow, использующих фоновую обработку (генерация печатных форм, парсинг XML, отправка сообщений):
* В E2E API-тестах запрещено рассчитывать на фиксированные задержки.
* Должны быть реализованы утилиты опроса состояния (Polling Pattern / Awaitility) с явным таймаутом и шагом проверки (например, опрос статуса задачи каждые 500 мс в течение максимум 10 секунд).
2. 🟨 Проверка таймаутов и падений фоновых задач
* Проверять поведение системы при сбое воркера (Dead Letter Queue / повторные попытки обработки Retry).

## Мокирование и эмуляция внешних интеграций
1. 🟥 Стандартизация мокирования внешних АИС и сервисов
* При проведении E2E и API-тестов внешние сторонние системы (например, внешние сервисы проверки контрагентов, смежные АИС) должны заменяться изолированными заглушками (WireMock, Microcks, Smocker).
* Код автотестового фреймворка не должен зависеть от доступности внешних контуров третьих лиц.
2. 🟨 Контрактное тестирование внешних интеграций (Pact / OpenAPI Mocks)
* Заглушки внешних сервисов обязаны валидироваться по согласованным OpenAPI/XSD-схемам интеграционного взаимодействия.


## Управление файлами и тестовым MinIO
1. 🟨 Изоляция и очистка тестового бакета MinIO
* При работе с MinIO автотесты должны создавать временные изолированные бакеты (или префиксы директорий) на время сессии/теста с гарантированным удалением созданных файлов (XML, PDF, подписи) в блоке teardown.
2. 🟩 Валидация генерации файлов без выгрузки на диск
* Сверка содержимого генерируемых EDI-документов (XML, JSON) должна по возможности выполняться в оперативной памяти (в виде бинарных потоков BytesIO), не нагружая локальный диск тестового ранера.

## Безопасность и управление доступами в тестовом фреймворке
1. 🟥 Ролевая модель и авторизационные токены
* В фреймворке автотестов должен быть реализован менеджер сессий/токенов (Auth Token Cache).
* *Зачем:* предотвратить повторную авторизацию (вызов /api/login) перед каждым API-тестом. Токен должен получать статус "валиден" и переиспользоваться для конкретной роли до истечения его exp (lifetime).
2. 🟨 Тестирование прав доступа (RBAC / ABAC)
* В структуру API-тестов должен входить параметризованный матричный тест: один и тот же эндпоинт вызывается под пользователями с разными ролями (Администратор, Оператор, Наблюдатель, Неавторизованный) с проверкой статус-кодов (200 / 403 / 401).

## Стандарты кода автотестов и структура тестового репозитория
1. 🟨 Единый стиль кода и статическая проверка (Linter & Formatter)
* Кодовая база автотестов на Python / TypeScript должна проходить статический анализ (Ruff/Flake8/Black для Python, ESLint/Prettier для TypeScript) перед сливом в основной репозиторий.
2. 🟩 Паттерны проектирования автотестов
* Для UI (Playwright) обязательно применение паттерна Page Object Model (POM) или Steps Component Model. Прямой поиск селекторов и клики внутри тела test(...) запрещены.
* Для API-тестов обязателен паттерн API Client / Service Layer (вынос HTTP-вызовов в отдельные методы-клиенты).

## Анализ причин упавших тестов (RCA) и процесс решения блокеров
1. 🟨 **Метки неисправленных багов в коде автотестов (@pytest.mark.xfail / test.fixme)**
* Если автотест упал из-за подтвержденного бага в приложении, который заведомо не будет исправлен в текущем хотфиксе/спринте, тест маркируется тегом @xfail(reason="БИТРИКС-1234") или test.fixme().
* *Результат:* тест не блокирует CI-пайплайн, но автоматически напомнит о себе (вызовет XPASS), как только разработчики исправят данный дефект.
2.Интеграция Allure TestOps / Test Management Systems (TMS)S)**
* Двусторонняя синхронизация: регулярный автоматический импорт результатов прогона из CI в систему управления тестированием для актуализации статуса покрытия требований.
