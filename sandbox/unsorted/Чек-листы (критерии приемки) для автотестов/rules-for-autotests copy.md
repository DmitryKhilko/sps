# СОЗДАНИЕ АВТОТЕСТОВ ДЛЯ EDI-FLOW
**Организация работ по созданию автотестов:**
- QA разрабатывает/актуализирует чек-листы проверки функционала программного продукта (реализующего бизнес-требования).
- BA, Dev делает ревью чек-листа перед созданием для него автотестов (PR в Gitea). 
- Dev создаёт/актуализирует автотесты.
- QA делает ревью автотестов, созданных по чек-листу (PR в Gitea). 
    - Проводится контроль соответствия автотестов чек-листу.  
    - Проводится контроль блока проверок - что именно проверяется. 

**Краткий набор требований по архитектуре тестового фреймворка и автотестов:**
- Автотесты пишутся на языке backend и frontend. В противном случае, автотесты будут умирать при уходе с фирмы создателя автотестов или их разработка замирать при уходе создателя в отпуск или на больничный.
- Архитектура фреймворка и автотестов backend и frontend должна быть разработана с участием лидов-разработчиков, понятна всем программистам. В противном случае - смотри пункт первый.
- E2E-сценарии должны быть независимыми: подготавливать перед началом и очищать после проведения тестовый набор данный.
- Для API-запросов E2E-сценария:
    - Сравнивать ожидаемый и фактический статус-код. 
    - Сравнивать тело ожидаемого и фактического ответа в зависимости от запроса в чек-листе: 
        - Полностью: response body (весь ответ: структура, форматы, данные).
        - Отдельный ключ: response body (значение статуса).
    - Требования к ожидаемым результатам:
        - Ожидаемый результат ответа может представлять собой JSON-схему, сформированную из Swagger / Pydantic-схем. После изменения в коде, вызванного изменением в требованиях/согласованным рефакторингом, ожидаемые ответы необходимо переформировать. 
        - До изменений в коде, вызванного изменением в требованиях/согласованным рефакторингом, ожидаемые результаты должны быть статичными. В противном случае возможна ситуация, когда ожидаемый результат "подстроится" под ошибочное изменение в коде и тест будет "зелёным". 
        - Тестовые значения для тела запроса (как валидные, так невалидные) генерировать на основе регулярных выражений (за исключением УНП, GLN, GTIN).   

**Возможный первоначальный план создания набора автотестов:**
- Этап первый. Создание E2E API-автотестов проверки сценариев создания партнерских связей.
- Этап второй. Создание E2E API-автотестов проверки сценариев движения ЭТН, ЭТТН, создаваемых в программном продукте и загружаемых из смежной системы.
- Этап третий. Создание E2E API-автотестов проверки сценариев регистрации работников СХ. 
- Этап четвертый - nn. Создание E2E API-автотестов проверки оставшихся сценариев (необходимо определить приоритетность оставшихся сценариев).
