## Возможный первоначальный план создания набора автотестов
- Этап первый. Создание E2E API-автотестов проверки сценариев создания партнерских связей.
- Этап второй. Создание E2E API-автотестов проверки сценариев движения ЭТН, ЭТТН, создаваемых в программном продукте и 
загружаемых из смежной системы.
- Этап третий. Создание E2E API-автотестов проверки сценариев регистрации работников СХ. 
- Этап четвертый - nn. Создание E2E API-автотестов проверки оставшихся сценариев (необходимо определить приоритетность 
оставшихся сценариев).
- Этап m - mm. Создание CRUD API-автотестов для сущностей EDI-Flow.
- Этап к - кк. Создание E2E UI-автотестов критичного функционала EDI-Flow (для типичных браузеров).   
- Этап z-zz. Создание UI Unit-автотестов для сущностей EDI-Flow (или создание аналогичных тестов с помощью Playwright).

## Общие требования по созданию автотестов
1. Для проверки качества EDI-Flow в рамках CI/CD будут запускаться следующие наборы автотестов: Unit/UI-Unit (проверка 
логики функций и изоляции UI-компонентов); API-E2E/интеграционные (проверка взаимодействия сервисов и бизнес-логика), 
UI-E2E на разных браузерах (проверка полной интеграции всех систем через интерфейс).  

2. Автотесты создаются на базе согласованного между BA + QA + Dev набора чек-листов (критериев приемки). В чек-лист не 
входят проверки, связанные с Unit-автотестами.   

3. Чек-лист может изменяться по мере разработки Dev автотестов, так как при целесообразности Dev может сделать 
дополнительные автотесты, не требуемые чек-листом. Или после оптимизации некоторые проверки чек-листа станут 
избыточными.  

4. Проверки в чек-листе имеют уникальный ID (например, CL-PARTNERSHIPS-API-01-001). Каждый автотест в коде **обязан** 
содержать этот ID в виде аннотации или тега.

## Инфраструктура автотестов
Если перечисленные выше наборы автотестов запускать последовательно, моя оценка длительности проведения автотестирования 
всего функционала EDI-Flow (регрессионное тестирование) - 4-5 часов (возможно больше). С учётом разбора причин падений 
автотестов, исправления выявленных багов и повторных перезапусков - затраты времени более 8 часов.

В IT-сообществе считается приемлемой длительность проведения автотестирования - 15 - 30 минут.

Для сокращения времени прогона регрессионного набора автотестов рекомендовано:   

1. Запуск автотестов в в изолированных Docker-контейнерах с использованием технологии Testcontainers.
- Контейнеры поднимаются один раз на всю тестовую сессию, а не перезапускаются ради каждого теста. 
- У Testcontainers есть поддержка Tmpfs (Temporary File System). Можно указать Docker-контейнеру записывать данные не на 
жесткий диск или SSD, а в виртуальную файловую систему в оперативной памяти. Что это дает:
    - Колоссальный прирост скорости: автотесты, которые активно пишут и читают (insert/update) в базу данных, начинают 
    работать в разы быстрее, так как минимизируются задержки на дисковые операции (I/O).
    - Чистота: как только контейнер останавливается, выделенная под него оперативная память мгновенно освобождается, а 
    данные исчезают без следа.

2. Настройка параллельных запусков автотестов. 
    - Параллельный запуск наборов автотестов позволит сократить время выполнения всех наборов. 
    - Один из инструментов, облегчающих параллельный запуск - Testcontainers.

## Архитектура автотестов
1. Главный принцип архитектуры автотестов (исключая Unit/UI-Unit): код автотестов и среда их запуска функционально 
отделены от кода приложения. Автотесты — это независимый «цифровой ОТК». Они проверяют систему на соответствие 
требованиям бизнес-аналитиков (BA), а не воспроизводят текущее поведение кода.
- Ожидаемые результаты, форматы, структуры и правила валидации автотестов запрещено генерировать динамически на основе 
текущего программного кода приложения (моделей, DTO, сущностей ORM). В противном случае баг в коде автоматически станет 
«эталоном» для теста. 
- Единственным источником правды для структуры API является зафиксированный контракт (например, заблокированный от 
самовольных изменений разработчиками Swagger/OpenAPI файл, согласованный с бизнес-аналитиками).
- Математические правила и алгоритмы валидации (например, вычисление контрольного числа в УНП/ИНН, маски документов) 
должны быть жестко зашиты в автотесты на основе требований BA. Если программист самовольно изменит валидацию в коде 
(например, разрешит буквы в УНП), автотест обязан упасть, зафиксировав дефект.

Пример автотеста:
```
def test_unp_validation():
    """ Проверка граничного значения и класса эквивалентности: буквы для УНП - невалидные данные"""
        
    # Присваиваем ИМЕННО В ТЕСТЕ (ИНОМ МЕСТЕ ФРЕЙМВОРКА) переменной заведомо 
    # ошибочный УНП с буквами (согласно требованиям BA)
    invalid_unp_letters = "ABCDEFGHI"
    
    response_letters = requests.post("http://localhost:8080/api/validate", json={"unp": invalid_unp_letters})
    assert response_letters.status_code == 400 
```

2. Управление тестовыми данными и граничными значениями.
- Необходимо преобладание динамически формируемых тестовых данных в проверках создания/изменения сущностей: оптимально, 
чтобы автотесты не использовали жестко зашитые (hardcoded) данные в телах запросов. Это позволяет избежать "эффекта 
пестицида", когда автотест не сможет найти баг при случайном/намеренном изменении кода, например, изменении допустимого 
набора символов или максимального значения числа.
- При генерации тестовых знаний для проверки граничных значений и классов эквивалентности, оптимально использовать 
абстракции: min-1, min, min+1, middle, max-1, max, max+1 - для граничных значений; valid, invalid - для классов 
эквивалентности. Текстовые поля могут генерироваться динамически на основе регулярных выражений (RegEx). 
    - Например, поле допускает значения от 5 до 10 символов кириллицы. Следовательно, операции создание/изменения 
    сущности должны быть проверены на значениях: "min-1, valid" - "абБф" (невалидное значение); "min+1, invalid" - 
    "aSwqiy" (невалидное значение); "middle, valid" - "ФашореКз" (валидное значение) и т.п.
    - Например, поле допускает значения (цифрами) от 0 до 1000. Следовательно, операции создание/изменения 
    сущности должны быть проверены на значениях: "min-1, valid" - "-1" (невалидное значение); "invalid" - 
    "aФы" (невалидное значение); "middle, valid" - "451" (валидное значение) и т.п.   
      
3. Степень детализации проверок API-автотестов. Автотесты **должны** поддерживать три уровня глубины проверок при 
валидации API-ответов (**выбор уровня диктуется чек-листом проверок**):
- Только статус-код: проверка соответствия HTTP-статуса (в E2E-автотестах).
- Статус-код + Ключевые атрибуты: проверка HTTP-статуса и конкретного ключа в ответе, например, статуса сущности 
(в E2E-автотестах). 
- Статус-код +  Полная сверка тела API-ответа:
    - Сравнение ответа целиком (используется DeepDiff или аналог).
    - На базе эталонной JSON-схемы динамически собирается пустой объект (dict), который наполняется отправленными в 
    запросе значениями.
    - Динамические ключи (ID, временные метки updated_at, токены) проверяются строго на формат/тип данных, но 
    игнорируются при сверке точных значений.
	- Область применения: обязательно для всех CRUD-операций создания и модификации сущностей.

4. Для CRUD-автотестов проверка успешности API-запроса не является достаточной. 
- Автотест обязан выполнять независимый прямой SQL-запрос (Raw SQL) в базу данных в ОЗУ, чтобы проверить корректность и 
полноту записи данных «бит-в-бит».
- Если бизнес-логика создает файлы и отправляет их объектное хранилище MinIO. Необходимо так же осуществить проверку 
созданного в MinIO файла. Например: напрямую извлечь из БД путь/ключ файла в MinIO; через MinIO-клиент скачать сам файл 
из бакета; выполнить валидацию содержимого «бит-в-бит» (для XML — проверку по XSD-схеме и вычитку ключевых тегов).

## Ревью автотестов / автотестового фреймворка
1. Созданный автотестовый фреймворк / автотесты будут подвергаться проверке на соответствие утвержденным требованиям 
несколькими ролями, в области своей компетенции (оптимально организовать проверку скриптами в рамках CI/CD):
- Lead Dev: инфраструктурные, архитектурные особенности фреймворка и автотестов.
- QA: соответствие автотестов чек-листу по количеству и составу проверок в автотесте; количество и состав запускаемых 
автотестов; результаты запусков автотестов.
