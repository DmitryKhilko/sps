## Содержание статьи
База знаний является (в том числе) "полигоном" для исследований способов создания и ведения документации для системы 
производства программных продуктов и для самих программных продуктов: порядков действий, требований к программному 
продукту, инструкций пользователя и т.д. 

Текущая статья содержит результаты проводимых исследований способов создания и ведения документации:
- объясняются причины выбора текущей архитектуры базы знаний;
- приводятся правила создания статей базы знаний.

## Стек технологий базы знаний
Перед созданием базы знаний были определены требования, которым должен удовлетворять выбираемый стек технологий: 
- Бесплатность инструментов для ведения базы знаний. 
- Доступность базы знаний и инструментов для её ведения в любой точке мира.
- Возможность групповой работы с базой знаний. 
- Версионирование статей базы знаний.
- Возможность сохранять копии базы знаний на персональный компьютер.
- Простота и скорость создания, изменения, публикации статей базы знаний.
- Возможность быстрого переноса базы знаний в иной репозиторий.
- Возможность загрузки базы знаний и её использования в [RAG-приложениях][6].

На основании приведенных выше требований для ведения базы знаний были выбраны инструменты:
- Репозиторий GitHub (центральное хранилище и система контроля версий):
    - Обеспечивает централизованное облачное хранение данных и синхронизацию файлов между различными рабочими станциями.
    - Ведёт непрерывный аудит изменений посредством фиксации коммитов, что позволяет восстанавливать предыдущие версии 
    документов и идентифицировать авторов правок.
    - Предоставляет инфраструктуру для совместной работы (механизмы Pull Requests и Issues) и разграничения прав доступа 
    пользователей.
- VS Code (интегрированная среда разработки и редактирования):
    - Служит локальным интерфейсом для высокопроизводительной обработки, сквозного поиска и модификации текстовых файлов.
    - Поддерживает конфигурирование под задачи ведения базы знаний за счет интеграции расширений (визуализация разметки, 
    управление Git-репозиторием).
- Markdown (формат разметки текстовых данных):
    - Это безальтернативный лидер для [RAG][8]: Использовать Markdown как целевой формат. Все остальные документы (PDF, 
    DOCX, HTML) должны конвертироваться в Markdown перед загрузкой в векторную базу.
    - Почему Markdown лучший выбор:
        - Идеальная структура для чанкинга: Заголовки (#, ##), списки и блоки кода в Markdown служат естественными 
        границами для разбиения текста. Это позволяет алгоритмам (например, MarkdownHeaderTextSplitter) делить документ 
        на смысловые блоки, не разрывая контекст.
        - Токен-эффективность: Markdown требует значительно меньше токенов для хранения той же информации по сравнению с 
        HTML (экономия до 25%), так как не содержит тегов, стилей и скриптов. Это снижает стоимость эмбеддинга и 
        генерации.
        - Чистота контента: В отличие от PDF, в Markdown нет проблем с «двойными колонками», «плавающими» картинками или 
        артефактами сканирования. Текст идет в правильном порядке чтения.
        - Легкость редактирования: Вы можете править базу знаний в любом текстовом редакторе, использовать Git для 
        версионирования и легко автоматизировать процессы (CI/CD для документации).
        - Обеспечивает долгосрочную сохранность и переносимость данных, поскольку файлы представляют собой плоский текст 
        (.md), независимый от программной среды.
        - Оптимизирует процессы контроля версий благодаря строчной структуре файлов, минимизирующей объем хранилища и 
        упрощающей дифференциацию (diff) изменений.

## Итеративно-инкрементный подход к созданию базы знаний
При создании статей базы знаний используется итеративно-инкрементный подход:
- Инкременты. База накапливается небольшими порциями: добавляется ровно то, что автор статьи знает и умеет на текущий 
момент времени. Каждая новая статья или раздел - это законченный, ценный результат, который можно использовать сразу.
- Итерации. Статьи пересматриваются, уточняются и улучшаются по мере получения новой информации и опыта у автора статьи. 

Такой подход позволяет избежать двух крайностей:
- Не ждать «идеального момента», когда какая-то тема станет полностью понятной - база знаний начинает работать сразу, 
даже в начальном виде.
- Не накапливать устаревшей или ошибочной информации - регулярные итерации обеспечивают актуальность и точность 
информации, содержащейся в базе знаний.

## Структура и иерархия файлов базы знаний 
Организация файлов должна отражать логическую структуру базы знаний, что упрощает навигацию как для людей, так и для 
алгоритмов извлечения RAG-приложения (retrieval).

- **Единая тема на файл**: Каждый файл .md должен охватывать одну конкретную тему или сущность. Это предотвращает 
смешивание несвязанных контекстов внутри одного документа, что ухудшает качество поиска. Разбить большие документы на 
мелкие, самодостаточные модули. Вместо одного большого файла на 500 страниц создать несколько файлов, описывающих 
отдельные темы. Это позволит чанкеру выделять смысловые блоки без потери контекста.
- **Иерархия заголовков**: Использовать строгую иерархию заголовков (#, ##, ### и т.д.). Заголовки служат естественными 
границами для чанкинга (разбиения текста). RAG-системы часто используют заголовки как точки разрыва, чтобы сохранять 
смысловую целостность блоков.
    - Принцип "один файл - один заголовок # H1". Главное название статьи должно быть строго в первой строчке. Не 
    использовать больше одного заголовка # в документе.
    - Использовать строгую иерархию ## H2 -> ### H3 -> #### H4. 
    - Заголовки должны быть описательного характера и содержать ключевые слова.
        - Плохо: "Общие сведения", "Настройки".
        - Хорошо: "Итеративно-инкрементный подход к созданию базы знаний", "Устранение ошибок подключения к базе данных".
- **Плоская или древовидная структура папок**: Избегать чрезмерно глубокой вложенности папок. Или использовать плоскую 
структуру с уникальными именами файлов, или логические папки (например, products/, guides/), если это помогает 
фильтрации по метаданным пути.







- Сквозная навигация. RAG-приложение строит карту взаимосвязей между документами. Для этого ему нужны чёткие указатели. 
    - Использовать явные ссылки. Никогда не упоминать другие документы просто текстом. Всегда делать их кликабельными 
    ссылками Markdown: [Название](путь).
    - Использовать только относительные пути. Не использовать домены (https://...) или абсолютные пути диска (C:/...). 
    Ссылки должны вести на файлы внутри репозитория базы знаний ([Текст](../соседняя_папка/file.md)).  
    - Если в статье множество раз употребляется термин, описанный в глоссарии, ссылаться на термин в глоссарии только 
    при первом упоминании в тексте статьи (но не в заголовках статьи). Для RAG гиперссылки играют роль структурных 
    маркеров, но их избыток может навредить.
        - Семантический шум: При чанкинге (разбиении текста) гиперссылки часто превращаются в Markdown-конструкцию 
        [термин](url). Если таких конструкций в чанке десятки, они могут «размывать» векторное представление текста, 
        добавляя шум в эмбеддинги.
        - Разрыв контекста: Чрезмерное использование ссылок может привести к тому, что при парсинге текст будет разбит 
        на множество мелких фрагментов, что усложнит модели восстановление связного контекста.
        - Польза ссылок (Link-Aware RAG): Сами по себе ссылки полезны - продвинутые RAG-системы используют их для 
        навигации (агенты могут «переходить» по ссылкам в глоссарий для уточнения сущностей). Но для этого достаточно 
        одной качественной ссылки на термин, а не сотни одинаковых.

## Написание контента статьи (RAG-friendly Writing)
Текст для RAG должен писаться иначе, чем текст для чтения человеком. Главная цель - сделать каждый абзац статьи базы 
знаний семантически плотным (в минимальный объем слов упакован максимум полезного смысла и фактов) и независимым.

[*Переход вверх*][3]

### Контекст и независимость разделов статьи 
При создании текста статьи базы знаний выполнить следующие условия:
- Избегать местоимений. В пределах одного текстового блока статьи (под одним заголовком) минимизировать использование 
слов «он», «она», «этот», «данный». Если абзац будет вырезан из контекста при чанкинге, модель не поймет, к чему 
относится местоимение. Рекомендуется заменять местоимения конкретикой: вместо "этот процесс" писать "согласование 
требований".
- Убрать канцеляризмы и эмоции. ИИ не нужны эпитеты «эффективный», «быстрый», «важнейший». ИИ нужны цифры и алгоритмы.
- Правило "первого предложения". Начинать каждый раздел (после заголовка) с краткого резюме или определения. Первое 
предложение должно отвечать на вопрос «О чем этот раздел?». Это помогает модели быстро классифицировать чанк.
- Самодостаточность (тематическая изоляция). 
    - Каждый блок статьи должен иметь смысл даже без чтения предыдущих блоков. Избегать фраз в стиле "Как написано в 
    текстовом блоке выше..." — при поиске ИИ может вырвать этот чанк отдельно, и контекст потеряется.
    - Необходимо повторять внутри текстового блока статьи ключевые термины и контекст, необходимые для понимания. 
- Тезисные формулировки. Использовать списки везде, где можно обойтись без связующего художественного текста.

[*Переход вверх*][3]

### Форматирование текста статьи 
При форматировании создаваемого текста статьи базы знаний выполнить следующие условия:
- **Не использовать таблиц в тексте**: Таблицы сложны для парсинга и часто "ломаются" при чанкинге - строки таблицы 
могут попасть в разные векторы. Рекомендовано заменить таблицы на маркированные или нумерованные списки с чёткой 
структурой.
- **Использовать вводные фразы для списков**: Перед списком всегда приводить полноценное предложение, объясняющее суть 
перечисления. Вводные фразы для списков связывают элементы списка в единый смысловой блок.    
- **Начинать каждый пункт списка с новой строки**: Пункты списка не располагать в одну строчку через запятую (точку с 
запятой).
- **Использовать единый символ выделения пункта маркированного списка**: Для единообразного представления пунктов 
маркированных списков по все базе знаний использовать один и тот же символ: звездочку * или дефис -.
- **Использовать нумерованные списки только для последовательных шагов (алгоритмов)**: Если для пунктов списка порядок 
не важен, для выделения пунктов списка использовать маркеры.
- **Использовать в пунктах списка констукцию "Ключ: Значение."**: 
    - "Ключ" - обобщающая фраза пункта списка, объясняющая суть пункта списка. Обобщающую фразу выделить полужирным 
    начертанием для усиления визуальньного и семантического веса. 
    - Двоеточие - сильный семантический сигнал «определения» или «списочности». Модели обучены воспринимать текст после 
    двоеточия как раскрытие темы до него.
    - Если "Значение" является описанием или правилом, вывод текста начинать с большой буквы, заканчивать точкой. 
    Например, "**Длина пароля**: Не менее 12 символов." 
    - Если "Значение" является параметром, кодом - вывод текста начинать с малькой буквы, не заканчивать точкой. 
    Например, "**Пароль**: сложный". 
    - Констукция "Ключ: Значение." позволяет:
        - Повысить точность поиска (матчинг заголовка с запросом).
        - Улучшить понимание моделью (четкая связь «свойство — значение»).
        - Сделать текст сканируемым для человека.
        - Помочь чанкеру сохранять логическую целостность блоков.
- **Дублировать рисунки текстом**: RAG-приложения (особенно текстовые) не "видят" картинки. Любую важную информацию из 
схем, скриншотов и диаграмм дублировать текстом, например, в подписи или в виде замещающего рисунок описания.
- **Не использовать в тексте статьи базы знаний эмодзи, иконки, декоративные элементы, спецсимволы**: Для надежной, 
предсказуемой и дешевой RAG-системы база знаний должна быть максимально «скучной». Чистый текст, четкая структура 
Markdown, никаких визуальных украшательств. Это гарантирует, что поиск будет работать по смыслу, а не по совпадению 
спецсимволов.
    - Эмодзи в тексте запретить: Использовать обычный текст, жирное начертание.
    - Эмодзи в заголовках запретить: Использовать иерархию #, ## и т.д.
    - Эмодзи в списках запретить: Использовать маркеры -, *, 1.
    - Декоративные картинки, иконки убрать из MD-файлов.
    - Инфографика/схемы	описать текстом: Alt-текст, описание под картинкой. 
    - Визуальные акценты: Использовать MD-форматирование (Цитаты >, блоки кода ```).

## 3. Метаданные и атрибуты
Ручное добавление метаданных значительно повышает точность поиска, позволяя фильтровать результаты еще до векторного 
сравнения.

* **YAML Frontmatter**: В начале каждого MD-файла добавляйте блок метаданных.
    ```yaml
    ---
    title: "Настройка резервного копирования"
    category: "Administration"
    product: "Server v2.0"
    tags: ["backup", "restore", "admin"]
    audience: "sysadmin"
    ---
    ```
    Это позволит вам в запросе к RAG указывать: *«Ищи только в категории Administration для продукта Server v2.0»*.[3]
* **Явные идентификаторы**: Если у объектов есть ID (артикулы, коды ошибок), упоминайте их в тексте явно и в разных форматах (например, «Ошибка 404», «HTTP 404», «Код 404»), чтобы повысить вероятность совпадения с запросом пользователя.[8]

## 4. Оптимизация под сценарии использования

Адаптируйте контент под то, как пользователи будут задавать вопросы.

* **Формат «Вопрос — Ответ»**: Включайте в текст явные вопросы, которые могут возникнуть у пользователя, и сразу давайте на них ответы. Это создает идеальные паттерны для retrieval.
    * *Пример*: «**Как сбросить пароль администратора?** Для сброса пароля выполните команду...».[1][5]
* **Сценарии (Session Starters)**: Для сложных процедур добавляйте вводный блок «Когда это использовать». Это помогает системе отсечь нерелевантные инструкции, если пользователь спрашивает о другом сценарии.[1]
* **Тестирование на реальных вопросах**:
    1. Соберите 10–20 реальных вопросов пользователей.
    2. Попробуйте найти ответы в вашей БЗ вручную или через прототип RAG.
    3. Если ответ не находится или неполный — перепишите соответствующий раздел, добавив недостающие ключевые слова и контекст.[9][10]

## 5. Чек-лист качества документа

Перед загрузкой файла в базу проверьте его по этим пунктам:

1. [ ] **Заголовок H1** уникален и точно описывает содержание.
2. [ ] **Метаданные** (Frontmatter) заполнены (категория, теги).
3. [ ] **Нет «висячих» местоимений** (понятно ли, что такое «он» в отрыве от контекста?).
4. [ ] **Таблицы заменены** на списки или описательный текст.
5. [ ] **Картинки описаны** текстом (важная информация не только на изображении).
6. [ ] **Разделы самодостаточны** (можно читать любой раздел без обязательного чтения введения).
7. [ ] **Ключевые слова** из запросов пользователей встречаются в заголовках и первых предложениях.[4][6][8]

Чек-лист автора перед сохранением файла:
1. Заголовок # ровно один и стоит на первой строке (после метаданных).
2. Все ссылки на другие файлы БЗ оформлены как [Текст](../путь/файл.md).
3. В тексте нет ссылок на локальный диск C://Users/....
4. Списки оформлены через *, а не через дефисы в строчку.
5. Заполнен блок метаданных в начале файла.


Соблюдение этих правил превратит вашу базу знаний из простого хранилища файлов в оптимизированный датасет, который обеспечит высокую точность и релевантность ответов RAG-системы.
